# ACARS-декодер для AOR AR5000 (свой проект на C, Windows)

Собственный декодер ACARS, ориентированный на приёмники без IQ-выхода
(SDR), такие как AOR AR5000 — сигнал заходит через звуковую карту, а не
через RTL-SDR/Airspy, как в большинстве версий `acarsdec`.

Архитектура написана "с нуля" на C, но опирается на ту же логику
протокола, что и оригинальный `acarsdec` (Thierry Leconte): модуляция
FFSK/MSK 2400 бод (тоны 1200/2400 Гц) с NRZI-кодированием, формат кадра
ARINC 618 (SYN SYN SOH, Mode, Addr, Ack/Nak, Label, STX+текст+ETX,
2-байтный BCS/CRC).

## Главное обновление: найден и исправлен настоящий корень проблемы

Присланный файл `131_725000_17_if.wav` долго не декодировался, и было
испробовано много попыток (сквелч по всплескам, подбор фазы, когерентный
АМ-демодулятор и т.д. — см. хронологию ниже) с результатом "0
сообщений". Все эти попытки чинили СЛЕДСТВИЯ, а не причину. Настоящая
причина обнаружилась только после того, как получилось прогнать
декодер на **официальном эталонном файле** проекта `acarsdec`
(`test.wav`, 7 заведомо известных сообщений) — и получить те же самые
"0 сообщений" на чистой, некогда-снятой-с-реального-эфира записи. Раз
эталонный, заведомо декодируемый файл тоже не декодировался — дело
было не в качестве присланной пользователем записи, а в самом
декодере. Нашлись и были исправлены три настоящих бага плюс один
неполный по возможностям алгоритм:

### Баг 1 — framesync.c искал голый SOH, без SYN SYN

Оригинальный `acarsdec` синхронизируется в три ступени: сначала ищет
байт SYN (`0x16`), затем требует, чтобы СЛЕДУЮЩИЙ байт-выровненный байт
ТОЖЕ был SYN, и только тогда ждёт SOH (`0x01`). Наша более ранняя
версия искала SOH сразу, скользящим окном по любому битовому сдвигу.
На реальном (а не синтетическом) сигнале граница "конец преамбулы
(долгий тон-маркер) → начало данных" сама по себе естественным образом
создаёт битовый паттерн `10000000`, который скользящий поиск SOH
воспринимает как начало кадра — ложно, задолго до настоящего SOH. Все
следующие байты кадра при этом читаются со сдвигом и не проходят CRC.
Требование ДВУХ подряд идущих байт-выровненных SYN перед SOH снижает
вероятность случайной ложной синхронизации на порядки.

### Баг 2 — CRC считался неправильно (включал SOH)

В настоящем ACARS контрольная сумма (BCS) считается от байта Mode до
ETX/ETB включительно — SOH (как и SYN SYN) в неё не входит, это чисто
служебные байты синхронизации. Наша более ранняя версия ошибочно
включала SOH в расчёт CRC. Из-за этого даже идеально принятый, без
единой ошибки бит, кадр НИКОГДА не прошёл бы проверку CRC.

### Баг 3 — не было NRZI-декодирования

Физический уровень ACARS использует NRZI: тон **не изменился** между
соседними битовыми интервалами → бит "1"; тон **изменился** → бит "0"
(подтверждено несколькими независимыми источниками, см. ссылки в
`demod.h`). Более ранняя версия декодера брала тон напрямую как
значение бита, без этого шага.

По отдельности каждый из этих трёх багов уже гарантированно ломал
декодирование ЛЮБОГО реального сигнала — неважно, насколько хорош
демодулятор. Все три исправлены.

### Неполнота алгоритма — простой дискриминатор недостаточен

Даже после исправления всех трёх багов эталонный `test.wav` всё ещё не
декодировался. Проверка эталонным методом (мгновенная частота через
преобразование Гильберта — математически точная, без приближений
однополюсного IIR-фильтра) с полным перебором фазы на "родной" частоте
дискретизации тоже не находила чистого совпадения SYN-SYN-SOH ни на
одном сдвиге. Вывод: дело не в частностях демодулятора, а в отсутствии
адаптивной тактовой синхронизации внутри пакета — простая выборка по
фиксированной сетке (даже идеальная) не может угнаться за реальным
сигналом.

Решение — честный порт настоящего демодулятора `msk.c` из оригинального
`acarsdec` (через подробно прокомментированный и построчно сверенный с
C-источником Rust-порт `sdr-acars`, см. ссылки ниже): согласованный
фильтр (133 отвода, обрезанный косинус под тон 1200 Гц) + ФАПЧ
Гарднер-типа, подстраивающая скорость битового потока по знаку
квадратурной компоненты на каждый бит. Это `src/mskpll.c` — работает на
"родной" для алгоритма частоте 12500 Гц (в неё передискретизируется
вход), не требует ни сквелча, ни перебора фазы: сам отслеживает дрейф
тактовой частоты передатчика на протяжении всего канала.

**Результат:**
- Эталонный `test.wav` проекта `acarsdec`: **7 из 7** сообщений, CRC
  сошёлся у каждого честно, без единой правки бита.
- Присланный пользователем `131_725000_17_if.wav`: **4 сообщения** с
  правдоподобным содержимым (адреса `.VP-B...` — один и тот же
  бортовой блок регистрации в разных сообщениях на одной и той же
  частоте, что убедительно свидетельствует о правильном декодировании,
  а не о случайном совпадении CRC).

Старый простой дискриминатор (`src/demod.c`) с перебором фазы
(`src/bitsync.c`) и делением на всплески (`src/squelch.c`) оставлен как
**резервный метод** — запускается только если `mskpll.c` не нашёл ни
одного сообщения. На практике на реальных сигналах он ни разу не нашёл
того, что не нашёл бы `mskpll.c`, но лишним не будет как страховка.

**Источники для порта `mskpll.c`:**
- Оригинальный `acarsdec` (Thierry Leconte): <https://github.com/TLeconte/acarsdec/blob/master/msk.c>
- Комментированный Rust-порт `sdr-acars` (построчно сверен с C-источником): <https://docs.rs/crate/sdr-acars/latest/source/src/msk.rs>, <https://docs.rs/crate/sdr-acars/latest/source/src/frame.rs>
- Эталонный тестовый файл: <https://docs.rs/crate/sdr-acars/latest/source/tests/data/acars_test.wav>
- Подтверждение NRZI-кодирования физического уровня ACARS: несколько независимых источников (Wiley "Specific Emitter Identification..." 2022, "Technical Handbook for Radio Monitoring VHF/UHF" 2013, allsdr.blogspot.com)

методом Гёрцеля с перебором остальных фаз как страховкой) и коррекция
одного битового сбоя по CRC в `framesync.c`. На синтетике всё работало,
на реальном файле — 0 сообщений.

**Попытка 3 — когерентный АМ-демодулятор (`coherent_am.c`).**
Гипотеза: диодный (нелинейный) детектор хуже борется с шумом, чем
линейный когерентный с прицельным полосовым фильтром вокруг несущей.
Реализован, при этом обнаружилось, что на зашумлённом синтетическом
сигнале когерентный метод неожиданно оказался ХУЖЕ диодного (фазовые
искажения биквад-фильтра между тонами 1200/2400 Гц), поэтому используется
только вторым заходом. Также обнаружены и отфильтрованы ложные CRC-совпадения
при переборе многих фаз/битовых правок (`fields_look_sane` в `framesync.c`).
На реальном файле — всё ещё 0 сообщений (что тогда списали на качество
записи — ошибочно, см. выше).

**Попытка 4 — поиск независимого эталона.** Найден `test.wav` проекта
`acarsdec` (см. выше) для проверки на заведомо декодируемом сигнале. По
пути обнаружен и исправлен реальный баг многоканального WAV:
`wav_load_mono()` усреднял ВСЕ каналы в один поток, что для файла с
несколькими независимыми радиоканалами (как раз `test.wav`, 4 канала)
гарантированно портит сигнал. Добавлены `wav_get_num_channels()` /
`wav_load_channel()`, `main.c` декодирует каждый канал отдельно.

Именно после того, как эталонный `test.wav` (уже с исправленным
многоканальным WAV) ВСЁ РАВНО дал 0 сообщений, стало ясно: дело не в
присланном файле, а в самом декодере — что и привело к находкам,
описанным в разделе "Главное обновление" выше.

## Что проверено (актуально на сейчас)

- WAV-ридер (`src/wavio.c`), моно и многоканальный (канал за каналом
  без усреднения), + линейный ресемплер.
- Диодный АМ-детектор огибающей с автоопределением (`src/ifdemod.c`) —
  для "сырых" IF-записей без встроенного АМ-детектора.
- Когерентный АМ-демодулятор (`src/coherent_am.c`) — вторая попытка
  АМ-демода в резервном конвейере.
- **`src/mskpll.c` — основной демодулятор**: согласованный фильтр +
  Гарднер-ФАПЧ, честный порт `msk.c` оригинального `acarsdec`.
- `src/demod.c` + `src/squelch.c` + `src/bitsync.c` — резервный
  конвейер (простой дискриминатор, деление на всплески, перебор фазы).
- `src/framesync.c` — трёхступенчатая синхронизация SYN-SYN-SOH,
  корректный расчёт CRC (без SOH), коррекция одного битового сбоя (для
  резервного конвейера), разбор полей.
- `src/selftest.c` синтезирует настоящий MSK-сигнал (с преамбулой
  SYN SYN SOH, NRZI-кодированием, корректным CRC) и прогоняет его через
  полный конвейер — сообщение успешно декодируется, включая текст.
- **Эталонный `test.wav` проекта `acarsdec`: 7 из 7 сообщений**, CRC
  сошёлся честно у каждого.
- **Присланный пользователем `131_725000_17_if.wav`: 4 сообщения**
  с правдоподобным содержимым.
- Многоканальный WAV: синтетический 2-канальный тест с разными
  сообщениями на разных каналах — оба декодируются независимо и верно.

`src/audio_win.c` (живой приём) переписан на классическое Win32
Multimedia API (`waveIn*`, `winmm.dll`) специально ради поддержки
Windows XP — см. раздел "Поддержка Windows XP" ниже. Написан по
документированному API, но **не компилировался** в этой сессии — здесь
нет Windows-тулчейна. Собрать и обкатать его нужно будет на вашей
машине.

## Поддержка Windows XP

Изначально живой приём был написан на WASAPI — современном API, которого
на XP физически нет (появился только в Vista). По просьбе пользователя
модуль **переписан на `waveIn*`** (тот же Win32 Multimedia API, что
использовался ещё в Windows 95/98) — он не менялся десятилетиями и
одинаково доступен от XP до Windows 11. Больше не нужно собирать два
разных `.exe` под старые и новые системы — один и тот же файл работает
везде.

Что именно изменилось:
- `IMMDeviceEnumerator`/`IAudioClient` (WASAPI, COM) → `waveInOpen`/
  `waveInPrepareHeader`/`waveInAddBuffer` (`waveIn*`, обычные функции,
  без COM) — заодно код стал проще и короче.
- При открытии устройства перебираются несколько частот дискретизации
  (48000 → 44100 → 22050 → 11025 → 8000 Гц) — на случай совсем старой
  или дешёвой звуковой карты эпохи XP, которая не умеет 48 кГц.
- Заодно живой приём подключён к основному конвейеру декодирования
  (`mskpll.c` — согласованный фильтр + Гарднер-ФАПЧ), а не к старому
  простому дискриминатору, как было раньше: раньше этот файл вообще не
  был связан с находками из раздела "Главное обновление" выше.

**Важная оговорка про русский текст в консоли.** До Windows 10 (версии
1903, 2019 год) консоль `cmd.exe` не умела по-настоящему отображать
UTF-8 — а исходники программы в UTF-8. На XP/Vista/7/8 вызов
`SetConsoleOutputCP(CP_UTF8)` при старте программы просто не сработает
(программа это обнаружит и предупредит), и русский текст в окне
консоли будет нечитаемым набором символов. Сама программа при этом
работает и декодирует правильно — проблема только в отображении.
Рабочий обход: перенаправьте вывод в файл и откройте его в любом
редакторе с поддержкой UTF-8 (например, Notepad++):
```
acarsdecoder.exe -l 2 > log.txt
```
и открыть `log.txt` — байты там корректный UTF-8 независимо от того,
что показывает сама консоль.

**Для сборки под XP через Visual Studio** дополнительно нужен набор
инструментов с поддержкой XP (в установщике Visual Studio — компонент
"MSVC ... build tools (v141_xp)" или аналогичный для вашей версии VS);
обычный современный рантайм MSVC на XP не запустится, даже если сам код
XP-совместим. Через MSYS2/MinGW-w64 такой особой настройки не требуется
— достаточно собрать как обычно (см. ниже), MinGW сам по себе не
привязан к конкретной версии Windows.

## Сборка

**Собирать нужно только ОДИН раз.** Makefile/CMakeLists уже настроены на
статическую линковку под Windows (`-static`) — получившийся
`acarsdecoder.exe` ни от каких DLL библиотек MSYS2/MinGW не зависит.
После сборки скопируйте на флешку только сам `acarsdecoder.exe` (и,
если нужно, `test_signal.wav` для проверки) — запускается на любом
Windows-компьютере с AR5000 (в т.ч. XP), MSYS2 там ставить не нужно.

### Windows, MSYS2/MinGW-w64 (проще всего)

```
pacman -S mingw-w64-x86_64-gcc mingw-w64-x86_64-cmake make
cd acars_decoder
mingw32-make
```
Получите `acarsdecoder.exe` и `acars_selftest.exe` в этой же папке.
Проверьте, что exe действительно самодостаточный (например, на
компьютере без MSYS2, или просто убедитесь, что запускается после
`mingw32-make clean`, когда никакие временные файлы сборки уже не
нужны): скопируйте `acarsdecoder.exe` на флешку, вставьте в целевой
компьютер и запустите `acarsdecoder.exe -l` — если сразу ругается на
отсутствующую `.dll`, значит `-static` в Makefile почему-то не
подхватился (проверьте, что используете `mingw32-make`, а не
голый `gcc` без флагов сборки из Makefile).

### Windows, Visual Studio + CMake

```
cmake -B build -G "Visual Studio 17 2022" -A x64
cmake --build build --config Release
```
MSVC обычно и так линкует статически рантайм по умолчанию в Release;
если на целевом компьютере всё же ругается на отсутствие
`vcruntime140.dll` — поставьте на него Visual C++ Redistributable, либо
пересоберите с `/MT` вместо `/MD`. Для настоящей Windows XP см. также
оговорку про тулчейн `v141_xp` в разделе "Поддержка Windows XP" выше.

### Linux (для разработки/тестов на WAV, без живого приёма)

```
make
./acars_selftest      # самотест конвейера
./acarsdecoder -f test_signal.wav
```

## Графический интерфейс

Запуск `acarsdecoder.exe` **без параметров** (в том числе просто
двойным кликом в Проводнике) теперь открывает окно, а не консоль,
которая тут же закрывается — именно то, что раньше сбивало с толку.
Явно открыть его же можно и из консоли командой `acarsdecoder.exe --gui`.

Окно даёт то же самое, что и консольные `-l`/`-f`, но без необходимости
запоминать параметры командной строки. Раскладка окна — по разделам,
каждая логическая группа элементов на своей отдельной строке с
запасом по высоте (раньше несколько групп теснились на одной строке, и
при добавлении новых элементов легко было забыть сдвинуть что-то ещё
и получить наложение — так и произошло однажды; переделано набело,
координаты всех элементов проверены программно на пересечения):
- выпадающий список устройств записи звука + кнопка "Обновить";
- кнопка "▶ Начать приём" / "■ Остановить приём" — живой приём с
  выбранного устройства;
- кнопка "Открыть WAV-файл..." — обычный диалог выбора файла вместо `-f`;
- кнопка "Импорт JSONL..." — загружает ранее сохранённый журнал
  (`acars_log.jsonl`) обратно в программу, без исходного звука (см.
  раздел "Импорт журнала" ниже);
- окно вывода со всеми расшифрованными сообщениями, с автопрокруткой,
  цветной подсветкой (тёмная тема, см. ниже) и кнопкой "Очистить лог";
- кнопка "▤ Таблица" / "☰ Лог" — переключает окно вывода в табличный
  вид (колонки: время, источник, режим, борт, метка, расшифровка
  метки, текст). Клик по заголовку колонки сортирует таблицу по ней
  (повторный клик — меняет направление сортировки). Таблица заполняется
  напрямую из структуры разобранного сообщения (отдельный канал
  передачи данных, `msg_sink.c`), а не парсингом текста лога — так
  надёжнее. Колонка "Борт" дополняется типом самолёта и авиакомпанией
  из `aircraft_db.csv`, если файл загружен и регистрация нашлась (см.
  раздел "База данных бортов" ниже) — например
  `.VP-BSY — Boeing 737-8LJ (B738), Aeroflot`.
- кнопка **"Статистика"** — сводка по всем накопленным за сессию
  сообщениям (тому же хранилищу, что и у поиска, см. ниже): сколько
  всего сообщений, сколько уникальных меток/бортов, топ-10 самых
  частых меток и топ-10 самых частых бортов. Простой разовый снимок по
  запросу (обычное окно с сообщением), а не отдельная постоянно
  обновляемая панель.
- кнопка **"Маршруты"** — сводка по бортам, для которых удалось
  распознать маршрут (вылет/назначение) — см. раздел "База данных
  аэропортов" ниже.
- кнопка **"Неисправности"** — сводка найденных за сессию отчётов
  CFDIU (см. раздел "Отчёты о неисправностях" ниже). Каждая запись
  подписана бортом и временем приёма сообщения.
- кнопка **"Телеметрия"** — последнее известное за сессию значение
  топлива/температуры/ветра/координат/ETA/высоты по каждому борту
  (см. раздел "Телеметрия ASU/AFL" ниже), с явной подписью, от какого
  борта и на какое время эти данные (время последнего сообщения, из
  которого они взяты).
- кнопка **"Погода"** — все найденные за сессию сводки METAR, по
  станциям, без повторов (см. раздел "Погода METAR" ниже) — с пометкой,
  от какого борта и когда принято каждое сообщение (отдельно от
  собственного времени самой сводки METAR, которое тоже показано).
- кнопка **"Подробности"** — в отличие от "Маршруты"/"Телеметрия"/
  "Погода" (которые показывают только итоговые значения), это окно
  для каждого из последних 12 подходящих сообщений показывает борт,
  время, метку, ИСХОДНЫЙ текст целиком и построчную расшифровку: какой
  именно кусок текста что означает, например `"FUEL   69"  ->  Топливо:
  69` или `"19006KT"  ->  ветер: направление 190°, скорость 6 KT`.
  Удобно, чтобы увидеть не просто "вот ответ", а откуда каждое значение
  взялось в исходном тексте.
- кнопка **"Карта"** — встроенная карта прямо в программе, как в
  трекерах рейсов: подложка OpenStreetMap, на позиции каждого борта
  значок самолёта (повёрнут по курсу), подпись с регистрацией и
  высотой, след из прошлых позиций, справа — список бортов и подробности
  выбранного. См. раздел "Встроенная карта" ниже.

**Про объём данных**: все перечисленные выше окна-отчёты (кроме
"Карты" — у неё своё окно), а также
"Статистика", "Диагностика", "Список памяти", открываются в отдельном
прокручиваемом окне с обычной вертикальной полосой прокрутки — не во
всплывающем MessageBox, который не умеет прокручиваться и плохо
справляется с большим текстом. Окно одно на всё приложение и
переиспользуется — повторное нажатие любой из этих кнопок просто меняет
его содержимое, не открывая новых окон поверх старых; крестик окна его
прячет, а не закрывает насовсем.

**Поиск внутри этого окна**: сверху — поле поиска и кнопка "Найти
далее" (или просто Enter прямо в поле). Регистронезависимый, ищет по
всему показанному тексту (борт, частота, текст сообщения, расшифровка
— что угодно), от предыдущей находки и дальше; дойдя до конца —
переносит поиск в начало по кругу, а не останавливается молча.
Найденное слово подсвечивается цветом фона (не обычным выделением —
оно у неактивного окна почти не видно на тёмной теме), независимо от
того, где сейчас находится фокус ввода, так что повторный Enter в поле
поиска ищет дальше, не теряя подсветку предыдущей находки. Поиск
использует собственное сообщение RichEdit (`EM_FINDTEXTW`), а не
подсчёт позиций вручную — что важно: при ручном подсчёте позиции
расходились с тем, что ожидает сам контрол (RichEdit по-своему считает
переводы строк), и подсвечивалось случайное соседнее слово вместо
искомого — так дальше не будет. Рядом с кнопкой — подпись вида "3 из
15" (какая по счёту находка сейчас показана из скольких всего найдено
в тексте) или "ничего не найдено", если совпадений нет вообще; при
смене текста в поле поиска общее число пересчитывается заново. Ctrl+A
выделяет весь текст — работает и в поле поиска (выделяет то, что в нём
набрано), и в самом окне отчёта (выделяет весь показанный текст, чтобы
скопировать Ctrl+C) — где именно, зависит от того, какое из двух полей
сейчас в фокусе. Работает одинаково во всех этих окнах — поле/кнопка/
подпись часть самого окна-
просмотрщика, а не каждого отчёта по отдельности.

- кнопка **"Диагностика"** (в панели AR5000) — одним нажатием собирает
  то, что при любой странности с настройкой обычно приходится
  выяснять пошагово: рабочую папку программы (именно относительно неё
  ищется `aircraft_db.csv` и создаётся `acars_logs` — самый частый
  источник путаницы "файл же на месте!"), список найденных устройств
  записи, подключён ли AR5000, статус базы бортов (загружено записей /
  не найдена / формат не распознан).
- флажок **"Поверх всех окон"** — держит окно программы поверх других,
  удобно для фонового мониторинга, чтобы окно не терялось за другими
  программами.
- **значок в системном трее** — появляется при запуске (значок
  программы, тот же, что на панели задач). Двойной клик — открыть/
  показать окно, правый клик — меню "Показать окно"/"Выход". Сворачивание
  окна (кнопка "_" или системное меню) прячет его в трей вместо панели
  задач — приём продолжается в фоне, при первом таком сворачивании за
  сессию показывается поясняющая всплывающая подсказка.
- флажок **"Уведомления"** (выключен по умолчанию при первом запуске,
  дальше запоминается — см. раздел про `acars_settings.ini`) — при
  каждом новом достоверном сообщении: звуковой сигнал (системный звук
  "Asterisk" - тот же, что Windows использует для обычных уведомлений,
  уважает тему звуков пользователя, а не свой файл) + всплывающая
  подсказка из трея с кратким содержанием (борт, метка). Включить —
  поставить галочку.
- поле **"Поиск:"** рядом со строкой статуса — живой (без кнопки
  "применить", фильтрует сразу по мере ввода) регистронезависимый
  поиск по всем колонкам таблицы (время/источник/режим/борт/метка/
  расшифровка/текст). Все полученные сообщения хранятся отдельно от
  того, что сейчас видно на экране (до 5000 последних — при превышении
  старые вытесняются новыми), поэтому очистка фильтра всегда
  показывает полную историю сессии, а не только то, что попало в поле
  зрения таблицы на момент ввода текста поиска. Кнопка "Очистить лог"
  в табличном режиме чистит и это хранилище тоже — по-настоящему
  полная очистка, а не только видимой части.
- панель управления AR5000 по RS-232 (COM-порт, скорость, частота,
  пресеты частых частот ACARS) с цветным индикатором состояния и
  визуальной полосой уровня сигнала — см. раздел "Подключение AR5000".

Оформление — тёмная "радарная" тема с подсветкой лога по смыслу (см.
выше), плоские (`BS_FLAT`) кнопки в тон общему стилю и подписи-разделители
между смысловыми блоками элементов управления.

Реализовано на "голом" Win32 (без сторонних библиотек, кроме
стандартной библиотеки общих элементов управления Windows - Common
Controls, для табличного вида) — работает в том же самом `.exe`, что и
всё остальное, от Windows XP до 11 (см. раздел про XP выше). Это тонкая
надстройка: GUI просто вызывает те же `run_live_capture()`/
`decode_wav_file()`, что и консольный режим — вся логика декодирования
одна и та же, продублированной логики нет.

Консольный режим (`-f`, `-l`, `--list-devices` и т.д.) по-прежнему
работает как раньше, если запустить программу с параметрами —
графический интерфейс не заменяет его, а дополняет.

**Базовая механика (список устройств, живой приём, открытие и
декодирование файла) подтверждена пользователем** на реальной
Windows-машине через MSYS2/MinGW в процессе разработки. Тёмная тема
оформления, подсветка лога (RichEdit) и табличный вид (ListView,
`msg_sink.c`) добавлены уже после этого и пока не проверялись на
реальном запуске — написаны по стандартному Win32 API и внимательно
вычитаны вручную, но при первом запуске после этих изменений возможны
мелкие шероховатости. Из известных
нюансов: поскольку `.exe` собран как консольное приложение (чтобы
работали параметры командной строки), при запуске двойным кликом
окно консоли может на мгновение мелькнуть перед тем, как откроется
настоящий графический интерфейс (программа сама прячет его через
`FreeConsole()`, но полностью убрать самый первый кадр появления
системными средствами нельзя). Это чисто косметическая мелочь, на
работу не влияет.

## Запоминание настроек (`acars_settings.ini`)

Все настройки GUI теперь сохраняются при закрытии окна и подставляются
обратно при следующем запуске — обычный INI-файл
(`acars_settings.ini`) рядом с программой, тот же принцип, что и у
`aircraft_db.csv`/`airport_db.csv`. Запоминается: COM-порт, скорость,
устройство записи (по номеру в списке), последняя частота, режим,
полоса, выбранный банк памяти, положение и размер окна, флажки
"Поверх всех окон"/"Уведомления". Если файла нет (первый запуск) — всё
остаётся со значениями по умолчанию, как и раньше, без ошибок.

Флажок **"Автостарт приёма при запуске"** — если включён, при
следующем запуске программа сама подключится к AR5000 (если указан
COM-порт) и начнёт приём с сохранённого устройства записи, без
необходимости нажимать кнопки вручную. Делает это не мгновенно при
старте, а с небольшой задержкой (через `WM_TIMER`, ~0.9-1.6 сек) —
чтобы окно успело полностью появиться, и через те же обработчики
кнопок "Подключить"/"Начать приём" (не отдельным кодом) — значит,
все те же проверки и сообщения об ошибках (например, если устройство
записи пропало) сработают точно так же, как при ручном нажатии.

## Сохранение истории сообщений (`history_log.c`)

Все результаты работы программы собраны в одном месте — в папке
**`acars_logs`**, которая создаётся рядом с рабочей папкой программы
при первом запуске. Каждое достоверно расшифрованное сообщение (в
любом режиме — живой приём, декодирование файла из консоли или через
GUI) автоматически дописывается в два общих файла внутри нее:

- **`acars_logs/acars_log.csv`** — с заголовком, открывается в
  Excel/LibreOffice Calc, удобно сортировать/фильтровать по борту,
  метке, времени и т.д.
- **`acars_logs/acars_log.jsonl`** — "JSON Lines", один JSON-объект на
  строку, удобно для последующей программной обработки (скрипты,
  импорт в другие системы).

Оба CSV-файла (общий и отчёт по файлу ниже) начинаются с UTF-8 BOM
(байтовой метки порядка) — без неё Excel по умолчанию открывает CSV в
старой системной кодировке, и русский текст превращается в
нечитаемые "РћС‚С‡С‘С‚..."; с BOM Excel сразу правильно распознаёт
кодировку при обычном двойном клике по файлу.

Поля: время, источник (`live`, имя файла, `файл [канал N/M]`), статус
CRC (`OK`/`FIXED`), mode, addr, acknak, label, расшифровка метки,
block_id, суффикс (ETX/ETB), текст сообщения. Файлы только
дополняются — старые записи никогда не перезаписываются и не
теряются между запусками программы. Запись потокобезопасна (в GUI
живой приём и декодирование файла могут идти параллельно).

**При декодировании WAV-файла** (из консоли `-f`, или через кнопку
"Открыть WAV-файл..." в GUI) дополнительно создаётся **отдельный
отчёт в той же папке `acars_logs`** — `acars_logs/<имя_файла>.decoded.csv`
(сам WAV-файл может лежать где угодно на диске - в отчёт попадает
только имя файла, без пути). Он появляется СРАЗУ, ещё до
декодирования, и не пропадает, даже если в файле не нашлось ни
одного сообщения (тогда в нём останется только заголовок) — так
видно, что файл действительно был обработан, а не просто нет
результата. При повторном декодировании того же файла отчёт
перезаписывается заново (в отличие от общих `acars_log.csv`/`.jsonl`,
которые только растут).

## Встроенная карта (`map_view.c`, `geomap.c`)

Кнопка **"Карта"** открывает отдельное окно с картой и самолётами.

**Откуда берутся самолёты.** Из телеметрии ASU/AFL (метки 26/27, поля
`LATN`/`LONE`) во всех накопленных сообщениях — принятых вживую,
декодированных из WAV или загруженных кнопкой "Импорт JSONL...". Для
каждого борта запоминается весь след (до 48 последних позиций, повторы
одной и той же точки не засоряют след). Окно обновляется само раз в
пару секунд, пока открыто — новые позиции появляются без нажатий.
Если в приёме не было ни одного сообщения с координатами, карта
откроется пустой, а справа будет подсказка, что делать.

**Что на карте.** Значок самолёта на последней позиции; подпись
`регистрация  высота ft`; оранжевый след; клик по самолёту или по
строке списка выделяет борт (голубое кольцо) и показывает справа его
картинку (фото или силуэт, см. ниже), время, позицию, высоту, топливо, ETA, тип/оператора (если
загружена база бортов) и курс. Управление: колесо мыши — масштаб вокруг
курсора, перетаскивание — сдвиг, двойной клик — приблизить, стрелки и
`+`/`-` с клавиатуры, `F` или кнопка "Показать все" — подогнать вид под все
борта, флажок "Следы", кнопка "В браузере" — открыть выбранную точку на
openstreetmap.org.

**Плавность карты.** Тайлы читаются и декодируются **в отдельном фоновом потоке**,
а не во время перерисовки: окно только заказывает тайл и сразу рисует то, что
уже есть, поэтому карта не подвисает при сдвиге. Дополнительно:
- *запас по краям*: для кэша SAS.Planet заранее заказывается рамка шириной в
  один тайл вокруг кадра (с меньшим приоритетом, чем видимые), так что при
  сдвиге новые полосы обычно уже готовы; из сети заранее ничего не качается;
- *подстановка вместо пустых квадратов*: пока тайл не загрузился, на его месте
  показывается растянутый кусок тайла другого масштаба из уже загруженных (при
  приближении) или четыре сжатых тайла более мелкого масштаба (при отдалении) —
  карта не "проваливается" на секунду при каждом зуме; если ничего подходящего
  нет, остаётся цвет фона без рамок;
- *плавное растяжение для «дыр» в кэше*: если тайла этого масштаба в кэше нет совсем
  (область скачана на мелком масштабе, а на крупном — только частично), вместо
  него показывается кусок тайла более мелкого масштаба, растянутый в 2–16 раз
  с **билинейным сглаживанием** (каждый пиксель — взвешенное среднее четырёх
  соседних; обычное растяжение давало "кубики", особенно на подписях). Результат
  строится один раз, хранится в ячейке и заменяется настоящим тайлом, как только
  тот появится; в кадре строится не больше 6 таких подстановок (остальные —
  в следующих кадрах), чтобы кадр не подвисал. Резкость при этом не
  появляется: чтобы убрать размытие, нужно скачать этот участок на нужном
  масштабе (о том, чего не хватает, пишет подпись в углу);
- *вид «пустых мест»* (клавиша **M**, запоминается в `[Map] FillMode`): где тайла
  нужного масштаба в кэше нет совсем, можно показывать **растянутую картинку как
  есть** (по умолчанию), **приглушённую** (смешанную на 40 % с фоном — заплатка
  не бросается в глаза) или **ничего** (просто фон). Это важно для спутника с
  вшитыми подписями: подпись нарисована прямо в картинке тайла, поэтому в
  растянутом тайле она в 2–4 раза крупнее настоящих подписей рядом, и отделить
  её от картинки нельзя. Приглушение делает её менее заметной, режим «ничего»
  убирает совсем;
- *очередь с приоритетами*: сначала то, что видно сейчас, среди равных — самое
  свежее заказанное; при смене масштаба или стиля устаревшие запросы
  выбрасываются, а ответы на прежнюю папку кэша отбрасываются;
- *память*: до 360 готовых тайлов в памяти (раньше 128 — на большом окне кадр
  занимал почти весь кэш, и только что показанное вытеснялось);
- *перерисовка*: кадр собирается в постоянном буфере (раньше буфер размером с
  окно создавался заново при каждой перерисовке), а при сдвиге, масштабе и
  приходе тайла перерисовывается только карта — панель справа (текст, сжатое
  фото) не трогается.
В подписи в углу при загрузке пишется "(грузится: N)"; "Нет файла в кэше"
показывается только про тайлы, которых в кэше действительно нет, а не про те,
что просто не успели прочитаться.

**Ширина панели справа.** Границу между картой и панелью можно тянуть
мышью (курсор меняется на стрелку влево-вправо, посередине границы три
"бугорка"): шире — крупнее фото и больше места тексту, уже — больше карты.
Двойной щелчок по границе возвращает ширину по умолчанию (340). Пределы:
панель не уже 240 и не шире, чем остаётся 320 пикселей карте; ширина
запоминается (`acars_settings.ini`, раздел `[Map]`, ключ `PanelWidth`). Пока
выбран борт, список бортов сокращается до 6 строк, чтобы хватило места на
фото и данные; остальные борта по-прежнему выбираются кликом на карте.

**Картинка борта (работает и без интернета).** При выборе борта в панели
показывается его изображение. Программа подбирает его по трём уровням:

1. **Ваши собственные фото из папки `aircraft_photos`** рядом с программой
   (в рабочей папке, где появляется `acars_logs`). Папка создаётся самой
   программой при открытии карты; под силуэтом есть ссылка "Открыть папку".
   Интернет не нужен. Не нужно снимать каждый борт отдельно: фото можно
   привязать к **типу самолёта и к компании** — один снимок работает для всех
   подходящих бортов. Программа берёт то, что точнее, в таком порядке:

   | № | Что подходит | Пример имени файла |
   |---|---|---|
   | 1 | именно этот борт (регистрация или код Mode S) | `RA-73764.jpg`, `155B22.jpg` |
   | 2 | модель + компания | `A320-214_Aeroflot.jpg` |
   | 3 | тип + компания | `A320_Aeroflot.jpg` |
   | 4 | модель | `A320-214.jpg` |
   | 5 | тип | `A320.jpg`, `B738.jpg` |
   | 6 | компания | `Aeroflot.jpg` |

   Значения берутся из `aircraft_db.csv` (колонки `model`, `typecode`,
   `operator`), поэтому без этой базы работает только номер 1.
   **Важно:** в базе OpenSky у многих бортов (особенно российских) модель и
   компания не заполнены — тогда для такого борта правила 2, 3, 4 и 6 не
   срабатывают, а работают 1 (борт) и 5 (тип, он в базе есть почти всегда). Что
   именно известно о выбранном борте, видно в панели: строка вида "AIRBUS (A320)"
   без названия компании означает, что компании в базе нет. **Точные имена для
   конкретного борта программа сама пишет под силуэтом** ("Подойдут имена: …") —
   их можно просто скопировать. Правила сравнения: регистр, дефисы, пробелы и
   подчёркивания не важны (`a320 214`, `A320-214`, `A320_214` — одно и то же);
   расширение любое из `.jpg .jpeg .jpe .jfif .png .gif .bmp .tif .tiff .webp
   .avif .heic .heif`; компания — любое начало её названия не короче 3 букв
   (`Aeroflot`, `Aeroflot Russian`), поэтому `A320_Aeroflot` подходит к борту
   "Aeroflot Russian Airlines", но не к "Rossiya"; допустимы и кириллица
   (`A320_Аэрофлот`), и копии Windows (`A320 (1).jpg`), двойное расширение
   (`A320.jpg.jpg`), хвост `_2`. Фото чужого типа или чужой компании не
   подставляется. Под фото всегда написано, по какому правилу оно найдено и
   что это не обязательно этот борт.
   Файл проверяется при каждом щелчке по борту, перезапускать ничего не нужно.
   Большие снимки автоматически сжимаются до 1000 пикселей в ширину. Права на
   снимки — ваша забота: программа фото не поставляет и не скачивает для этого
   режима.
   **WebP, AVIF, HEIC** открываются средствами Windows (WIC), если в системе есть
   нужный кодек (на Windows 10 — "Расширения для изображений WebP / HEIF" из
   Microsoft Store; если приложение "Фотографии" такие файлы открывает, кодек уже
   стоит). Если кодека нет, панель об этом скажет. Если при сборке заголовок
   `wincodec.h` не подошёл, добавьте к флагам компилятора `-DMV_NO_WIC` — эта
   часть отключится, а остальная карта останется как есть.
2. **Фото из интернета** (необязательно, нужен интернет) — с сайта
   planespotters.net, если вы один раз указали свой контакт (см. ниже). Если
   своё фото есть, интернет не используется вообще.
3. **Силуэт по типу самолёта** — если фото нет совсем. Рисуется самой
   программой, всегда, без интернета: узкофюзеляжный реактивный (A319–A321,
   B737, E190, SSJ100...), широкофюзеляжный (A330, A350, B777, B787, Ил-96...) или
   турбовинтовой (ATR, Dash 8, Ан-24...). Тип берётся из `aircraft_db.csv`
   (колонка `typecode`); если базы нет или тип в ней не найден — рисуется
   узкофюзеляжный по умолчанию, с пометкой "тип неизвестен". Это **схема типа,
   а не фото конкретного борта**, об этом написано под рисунком; там же —
   подсказка, под каким именем положить свой файл.

*Если файл найден, но не открывается.* Программа читает первые байты файла и
называет его **настоящий** формат (расширение в имени ничего не гарантирует).
Типичный случай — картинка, сохранённая из браузера: имя `RA-73764.jpg`, а внутри
WebP или AVIF. GDI+ такое не читает, поэтому программа пробует открыть файл
средствами Windows (WIC, как приложение "Фотографии"); если кодека в системе нет,
панель так и пишет: "внутри не JPEG, а WebP … нет кодека". Тогда либо
установите "Расширения для изображений WebP" из Microsoft Store, либо откройте
файл в Paint и сохраните как JPEG. Если формат обычный (JPEG/PNG...), но файл
всё равно не открылся, значит он повреждён или слишком большой. Быстрая проверка
самому: открыть файл в Блокноте — у настоящего JPEG вначале видно `JFIF` или
`Exif`, у WebP — `RIFF` и `WEBP`.

*Если своё фото не показывается.* Под силуэтом программа пишет, **где именно
она ищет файл** (полный путь вида `F:\acars\aircraft_photos\RA-73764.jpg`) —
сравните с тем, где он лежит у вас. Типичные причины: имя не совпадает с
регистрацией борта в списке справа (`RA-73764`, а не `RA-73167`); файл лежит
в другой папке `aircraft_photos` (удобнее всего открыть нужную ссылкой "Открыть
папку aircraft_photos" под силуэтом и класть файл туда); скрытое расширение
(в проводнике включите "Показывать расширения имён файлов" — файл мог
оказаться `RA-73764.jpg.jpg`); формат, который GDI+ не умеет открывать: если
файл найден, но не открывается, панель так и напишет — это бывает у WebP
(часто сохраняется из браузера под видом `.jpg`) и HEIC с iPhone; пересохраните
как JPG или PNG. Фото проверяется при каждом щелчке по борту.

*Рабочая папка.* Относительно рабочей папки программы берутся
`aircraft_photos`, `acars_settings.ini`, `acars_logs` и кэш тайлов. Раньше
стандартный диалог "Открыть файл" (кнопки "Открыть WAV-файл..." и "Импорт
JSONL...") сам менял рабочую папку на папку выбранного файла — после этого
перечисленное искалось бы уже там. Теперь рабочая папка запоминается перед
диалогом и возвращается после него.

*Фото из интернета (Planespotters Photo API).* Клик по такому фото открывает
страницу снимка в браузере; под фото всегда написан фотограф — это
обязательные условия API. Если известен код Mode S борта (колонка `icao24` в
`aircraft_db.csv`), запрос идёт по нему и возвращается фото именно этого
экземпляра; иначе — по регистрации (для российских бортов дефис возвращается
автоматически: `RA73104` → `RA-73104`, в 7-символьное поле адреса ACARS он не
влезает). Если фото нет, пишется "не найдено"; если нет интернета — "сейчас
недоступно", повтор через минуту; в обоих случаях показывается силуэт.

*Включается один раз.* По правилам Planespotters программа в каждом запросе
должна представляться описательным `User-Agent` с **контактом владельца**
(почта или адрес сайта). Придумывать за вас контакт программа не может, поэтому
под силуэтом стоит подсказка: щелчок по ней откроет `acars_settings.ini` —
впишите свою почту или сайт после `Contact=` в разделе `[Photos]`, сохраните
файл. Фото появится само, перезапускать ничего не нужно. Пока контакт не
указан, никаких запросов в интернет не отправляется вообще, а своё фото и
силуэты работают как обычно.

*Что и куда уходит.* Только код или регистрация выбранного борта и ваш
контакт — на `api.planespotters.net`; картинка забирается с `cdn.planespotters.net`.
Запросы делаются только по щелчку на борт, по одному, без повторов в цикле.
*Что не делается.* Картинки из интернета не записываются в файлы (ни в папку
программы, ни в кэш WinINet — для этого запросы идут с флагом "не писать в
кэш"): они скачиваются прямо с адреса из ответа в память, показываются и
выбрасываются; ответ API помнится в памяти не дольше часа (условия
разрешают до 24 часов) и пропадает при закрытии программы. Именно поэтому
фото с Planespotters нельзя "накопить" для работы без сети — условия сервиса
запрещают их сохранение; для офлайна служит ваша папка `aircraft_photos`.
Адреса из ответа используются без изменений и принимаются только с сайтов
Planespotters. Фото без указанного фотографа не показывается.

*Оговорка.* Условия Planespotters написаны для веб-сайтов ("грузить в
браузере пользователя"); настольная программа, работающая на компьютере
самого пользователя и скачивающая картинку напрямую в память, — ближайший
аналог, но формально случай пограничный. Для личного пользования этого
достаточно; если вы собираетесь распространять программу другим людям,
сначала согласуйте это с Planespotters.

**Подложка и её стили.** Выпадающий список в верхней панели карты
переключает вид подложки; выбор запоминается (`acars_settings.ini`,
раздел `[Map]`, ключ `StyleId`).

| Стиль | Откуда берётся | Что это |
|---|---|---|
| OpenStreetMap (стандартная, из интернета) | скачивается, кэш в `acars_tiles` | по умолчанию, ничего настраивать не надо |
| Кэш SAS.Planet: проекция Яндекса (EPSG:3395) | готовые тайлы с диска | Яндекс, Космоснимки и т.п. |
| Кэш SAS.Planet: Web Mercator (Google/OSM/Bing) | готовые тайлы с диска | Google спутник/схема, OSM, Bing |
| Кэш SAS.Planet: Google гибрид (спутник + подписи) | **две** папки с диска | спутник с наложенным слоем подписей и дорог |

Стили CARTO и OpenTopoMap, бывшие в прошлых версиях, убраны вместе с
файлом `carto_key.txt`. Старые подпапки `acars_tiles\carto_*` и
`acars_tiles\opentopo` больше не используются, их можно удалить. Ранее
сохранённые стиль и папка кэша SAS.Planet (Яндекс, Web Mercator)
подхватываются автоматически.

Тайлы OSM скачиваются в фоновом потоке и сохраняются в папку
`acars_tiles\osm` — один раз показанная область потом открывается без
интернета. Если интернета нет (или недоступна `wininet.dll`/`gdiplus.dll`)
— вместо подложки рисуется координатная сетка, самолёты и следы
показываются как обычно; причина написана внизу карты. Внизу карты у
каждого стиля показана его подпись об авторстве — это требование лицензий.
Правила использования тайлов OSM соблюдены (осмысленный User-Agent, одно
соединение, кэш на диске), но это именно **личное** использование.

**Кэш SAS.Planet (Яндекс, Google и др.).** Программа ничего не скачивает
у этих сервисов, а читает готовые файлы с диска — работает и без
интернета.

1. В SAS.Planet скачайте нужную область нужной карты в кэш и держите
   его в формате "SAS.Планета" (обычные файлы; тип кэша — в настройках
   SAS.Planet, пункт "Тип кэша по умолчанию"). Если у вас кэш другого типа
   (например SQLite, папка `cache_sqlite`) — скопируйте область в этот
   формат: "Операции с выделенной областью" - "Копировать" - формат
   "SAS.Планета".
2. В окне карты выберите стиль "Кэш SAS.Planet: ..." и укажите **папку
   карты** — ту, внутри которой лежат папки масштабов `z8`, `z9`, ...
   (например, `...\cache\yamapng`). Типичные промахи программа прощает:
   выбрана папка масштаба (`z9`) — возьмёт её родителя; выбрана папка
   кэша, где лежит ровно одна карта, — возьмёт её; карт несколько —
   покажет список и попросит выбрать одну. Если папку выбрать не
   получается, в том же окне есть запасной вариант — указать любой файл
   тайла. Выбор запоминается; сменить папку можно кнопкой "Папка кэша...".
   При этом ничего не загружается: программа лишь запоминает путь и
   смотрит имена папок масштабов (чтобы узнать диапазон), а тайлы читает
   по мере надобности — только те, что нужны для видимой части.
3. **Выберите стиль под проекцию источника**, это важно: тайлы Google,
   OSM, Bing лежат в обычном Web Mercator (EPSG:3857), тайлы Яндекса и
   Космоснимков — в эллипсоидальном Меркаторе (EPSG:3395). Программа
   умеет считать в обеих проекциях, но какая из них у ваших тайлов, она
   по файлам определить не может. При ошибочном выборе всё на карте
   сместится по широте (на широте Нижнего Новгорода примерно на 20 км).
   Источники в проекции "широта/долгота" (SAS.Planet projection=3,
   например Google Earth) не поддерживаются.

Диапазон масштабов определяется по папкам кэша (`z1`, `z2`, ... —
номер в имени на единицу больше обычного масштаба: в SAS.Planet масштабы
нумеруются с 1, а в этой программе, как в OSM/Google/Яндексе, с 0, так что
"8-11" в SAS.Planet = "7-10" здесь; в подписи на карте показаны обе
нумерации), и масштаб карты ограничивается им: за пределами скачанного
были бы одни заглушки. В углу карты постоянно показано, какая папка, какая
проекция и какие масштабы используются. Если на участке тайлов нет, вместо
них рисуются заглушки и пишется, какие масштабы в кэше есть.

**Что показывает подпись в углу карты (кэш SAS.Planet).** Кроме папки, проекции и
масштабов, там написано "тайлов в кадре: N из M" — сколько тайлов нужно для
видимой области и сколько из них нашлось в кэше. Если нашлись не все, ниже
жёлтой строкой стоит **первый ненайденный** тайл, например
`Нет файла в кэше: z12\1\x1274\0\y634.*` — это путь внутри папки карты
(расширение любое). Достаточно открыть эту папку в проводнике и посмотреть, есть
ли там файл: если нет, этот масштаб скачан не для всей нужной области (или
копирование не закончилось). Диапазон масштабов обновляется сам, если в папку
кэша докопировали новый масштаб, пока карта открыта.

**Что докачать, если часть кадра размыта.** Резкости у растянутой картинки не
будет — взять её неоткуда. Подпись в углу карты показывает три строки: общий
итог ("тайлов в кадре: 27 из 54"), первый ненайденный тайл (`Нет файла в кэше:
z12\1\x1362\0\y583.*`) и **область для докачки в координатах**: "Не хватает 27
из 54 тайлов, масштаб SAS.Planet 12. Область для докачки: широта 61.02 ... 61.44,
долгота 59.41 ... 61.17". Эти значения можно ввести в SAS.Planet, выделив
прямоугольник по координатам, и скачать этот масштаб ровно для недостающей
области (название пункта меню в вашей версии SAS.Planet может отличаться).
Границы считаются по недостающим тайлам видимого кадра, поэтому область слегка
шире нужной (до целых тайлов).

Четвёртая строка даёт те же углы области **в градусах, минутах и секундах — в том
виде, в каком их принимает диалог SAS.Planet "Выделение по координатам"**:
`верхний левый угол N45°34'59.84" E63°37'58.13"` и `нижний правый угол
N44°50'25.05" E65°12'53.44"`. Верхний левый — северо-западный угол (северная
широта, западная долгота), нижний правый — юго-восточный. Минуты и секунды в
такой записи всегда меньше 60: если вписать, например, `44°96'`, SAS.Planet
ответит "Error in geographic coordinates" (96 минут не бывает) — частая ошибка при
ручном переводе из десятичных градусов (44,96° — это 44°57'36", а не 44°96').
Если в диалоге выбран формат десятичных градусов, можно вводить числа из
третьей строки как есть.

**Серые тайлы-заглушки.** Бывает, что в кэше на месте отсутствующих
участков лежат настоящие файлы, целиком залитые серым цветом
(192, 192, 192) — это "цвет пустого места" в SAS.Planet. Такой тайл —
не картинка, а пометка "данных нет", поэтому программа распознаёт его
(все пиксели серые с точностью до +-4, запас на сжатие JPEG) и рисует как
отсутствующий, то есть тёмной заглушкой. Сколько таких тайлов встретилось,
показано в подписи в углу карты: "пустых серых тайлов в кэше: N". Если
подпись не появилась, а серые квадраты остались, значит они не такого
цвета — тогда нужен сам файл такого тайла, чтобы разобраться. Чтобы серого
не было вовсе, копируйте в SAS.Planet именно ту область, которая реально
скачана.

Если в самих тайлах уже есть подписи городов (бывает, когда SAS.Planet
копирует карту сразу вместе с наложенным слоем), то стиль "Google гибрид"
не нужен — достаточно "Web Mercator": слой-наложение предназначен для
случая, когда спутник и подписи лежат в двух отдельных папках.

**Google гибрид (спутник + подписи).** В SAS.Planet "Google Гибрид" — это
не отдельная карта, а **прозрачный слой** (подписи городов, дороги), который
накладывается на "Google Спутник". Поэтому нужны два набора тайлов — и
программа накладывает один на другой сама:

1. В SAS.Planet скачайте и сохраните в файловый кэш на одну и ту же область
   и одни и те же масштабы и **спутник**, и **слой Google.Гибрид** (в окне
   загрузки слой выбирается так же, как карта).
2. В окне карты выберите стиль "Кэш SAS.Planet: Google гибрид". Программа
   спросит две папки по очереди: сначала **спутник**, затем **слой
   "Гибрид"**. Во втором вопросе можно ответить "Нет" — тогда будет просто
   спутник, без подписей.
3. Слой можно сменить отдельно кнопкой "Слой подписей..." (она видна только
   у этого стиля); основу — кнопкой "Папка кэша...".

Наложение делается при чтении тайла: пиксели слоя смешиваются с пикселями
спутника с учётом прозрачности (полностью прозрачный пиксель слоя оставляет
спутник как есть). Склеенный тайл потом хранится в памяти как обычный, так
что повторная прорисовка ничего не стоит. Если для какого-то тайла слоя нет,
показывается спутник без подписей, и наоборот. Предполагаются тайлы
256x256 (стандарт); тайлы другого размера не накладываются.

Программа сама ничего не скачивает у Яндекса, Google и подобных
сервисов — только читает файлы, которые у вас уже есть. Условия
использования источников, из которых SAS.Planet скачал эти файлы,
остаются на вашей стороне: у многих сервисов они ограничивают
массовое скачивание и использование вне их собственных приложений.

**Почему нет прямой загрузки Яндекс.Карт и Google.** Для Яндекса
предусмотрен только доступ через его API с обязательным ключом, а в
условиях бесплатной версии есть ограничения на задачи "мониторинга
транспорта" (отслеживание самолётов к ним близко). Поэтому программа
сама эти тайлы из сети не скачивает.

**Что нужно знать о данных, а не о картинке.**
- *Курс* самолёта на значке — не из бортовых систем (в этих сообщениях
  курса нет, `WDIR` — это направление ветра), а вычисляется как
  направление перемещения между двумя последними **разными** позициями
  борта (не ближе 0.5 км друг от друга — на меньшем расстоянии это шум
  округления координат). Пока позиция всего одна, значок смотрит на
  север, а в панели написано "курс неизвестен". Между сообщениями борт
  мог лететь по ломаной — это направление не обязательно совпадает с
  курсом в конкретный момент.
- *Высота* показывается так, как передана; по характерным значениям
  (35992, 36000, 34984) это футы — потому подпись `ft`, но единицы в
  самом сообщении не указаны.
- Позиция на карте — **на момент последнего принятого сообщения**, а не
  "прямо сейчас". Часто это минуты и более назад — время сообщения
  показано в панели.

**Оговорка о проверке.** Математика карты (проекция, номера тайлов,
курс, подгонка масштаба, разбор координат) проверена 15 тестами, включая
независимо посчитанные номера тайлов, твои реальные координаты, сверку
эллипсоидального Меркатора (проекции Яндекса) с независимой формулой и с
документированной широтой 85.084° верхнего края мира. Разбор путей кэша
SAS.Planet — 6 тестами (включая пример из документации), поиск папки карты
— 11 тестами на настоящем дереве папок (типичные промахи, несколько карт,
кириллица и пробелы). Фоновая загрузка тайлов (очередь с приоритетами, запас по краям, устаревшие
ответы, повторные попытки, переполнение очереди, подстановка соседнего масштаба,
освобождение подстановок) — 39 проверок; билинейное сглаживание — 8 проверок под
AddressSanitizer (точность по формуле, отсутствие швов и выхода за память у краёв);
приглушение и подсказка о докачке (координаты сверены с независимым расчётом) — 9 проверок;
перевод в градусы-минуты-секунды — 14 проверок, в том числе перебор 400 000 значений:
минуты и секунды никогда не выходят за 59. Свои фото и силуэты (без интернета): шесть правил привязки (борт, модель/тип + компания,
модель, тип, компания) на настоящих файлах и папках, ключи имён, подсказка по именам, кириллица,
идентификаторы COM для WIC, определение настоящего формата файла по байтам, категории типов
самолётов и геометрия силуэтов — 56 проверок. Разбор ответа сервиса фото, ключи запроса, проверка контакта и ширина
панели — 37 проверок (в том числе враждебные ответы: подмена адресов,
обрывы, лишние символы, юникод). Наложение слоя и определение серых заглушек: 18 проверок, в том числе перебор всех
16.7 млн сочетаний (пиксель слоя, пиксель основы, прозрачность) против
точной формулы — ошибка не больше половины градации, то есть обычное
округление; ещё 13 проверок — таблица стилей и перенос старых настроек.
Код выбора бортов проверен на настоящем `acars_log.jsonl`. Сам код окна
проверен на типы и объявления, но **запуск на живом Windows (чтение файлов
SAS.Planet и диалог выбора папки, декодирование PNG/JPEG средствами GDI+,
чтение пикселей и наложение, отрисовка) в этой среде проверить нельзя** —
если что-то поведёт себя не так, пришли скриншот или текст из строки
состояния внизу карты.

### Список бортов в панели карты прокручивается

В панели справа список «Борта с координатами» показывает 10 строк (6, когда выбран борт и
под списком нужна карточка). Остальные борта доступны так же, как первые: колёсико мыши над
панелью прокручивает список, справа от списка есть полоса прокрутки (клик по ней - переход в
нужное место), под списком написано «Борта 4-13 из 27». Клик по строке выбирает борт и
центрирует на нём карту; борт, выбранный кликом на карте, список сам прокручивает в видимую часть.

### Чистая карта (минимум служебной информации)

По умолчанию на карте с кэшем SAS.Planet показывается только строка «Масштаб N» - номер в
нумерации SAS.Planet (как в папках z8, z9, ...), одна цифра вместо двух. Нет подписи про права
на тайлы, нет счётчика «тайлов в кадре», а за пределами скачанной области просто пусто, без
сообщений «нет файла в кэше». Всё это - служебные сведения для докачки области - осталось
доступным: клавиша **I** включает и выключает подробный режим (проекция, диапазон масштабов,
счётчик тайлов, какого файла не хватает, углы области для SAS.Planet).

### Высота: метры и футы

Борт передаёт высоту в футах. Везде (карта, панель борта, консоль, расшифровка, Excel) она показывается
как «10973 м (36000 ft)»: сначала метры, в скобках исходные футы (1 ft = 0.3048 м). Если в поле не число
(например, прочерки), текст остаётся как есть.

### Выгрузка журнала с заданного времени (кнопка «Выгрузка...», `journal_export.c`)

Кнопка справа от «Импорт JSONL...». В окне задаётся период (время - местное, как записано в журнале):
**С** (по умолчанию сегодня 00:00) и **По** (пусто - до конца журнала); форматы `06.10.2026 14:30`,
`2026-10-06 14:30`, `06.10.2026`, `14:30` (сегодня). Источник - журналы `acars_logs\acars_log.jsonl` и
`acars_log.jsonl` рядом с программой (те же, что читает автозагрузка); повторы между ними отбрасываются.

Два формата:
- **Excel (.xlsx)** - три листа. «Сообщения»: одна строка на сообщение, 25 колонок - время (настоящая
  дата-время Excel), приём, борт, тип самолёта, оператор, метка и её смысл, рейс, авиакомпания, событие,
  откуда/куда (с названием аэропорта), широта/долгота, высота в метрах и футах, топливо, ETA, температура,
  ветер, время события, расшифровка по-русски и исходный текст; шапка закреплена, включён фильтр.
  «Борта»: сводка по каждому борту (сколько сообщений, первое/последнее, последний рейс, позиция, высота).
  «Пояснения»: что означает каждая колонка и что в ней не подтверждено. Файл создаётся самой программой,
  устанавливать Excel для этого не нужно (читают Excel, LibreOffice и др.).
- **JSONL** - строки журнала как есть, только за выбранный период (формат совместим с «Импорт JSONL...»).

Галочка «Без служебных сообщений» убирает подтверждения `_`, проверку канала `Q0` и `SQ` - обычно это
больше половины журнала и пользы для чтения в них нет (для Excel включена по умолчанию, для JSONL - выключена).
Тесты: `tests/test_export.c` (выгрузка реального журнала, проверка файла сторонними средствами).

### Цвета бортов и маршрут по следам

**У каждого борта свой цвет** (12 различимых оттенков): значок самолёта, линия следа, подпись на карте и
квадратик в списке справа одного цвета - видно, какой след чей, даже когда бортов много. Значок крупнее
прежнего, выбранный - ещё крупнее, с белой каймой и кольцом. Подписи, которые наехали бы друг на друга,
пропускаются (у самолёта остаётся цвет и строка в списке); у выбранного борта подписи показываются всегда.

**Маршрут по следам.** Каждое сообщение с новой позицией - точка следа, и для каждой точки запоминаются время,
высота, топливо и ETA из этого сообщения. У выбранного борта на карте:
- точки пронумерованы (1 - самая старая), рядом подпись `номер  широта  долгота  время`;
- последняя точка - сам самолёт, его координаты подписаны рядом;
- клик по точке на карте выбирает её (белая кайма и жёлтая подпись);
- в панели справа таблица «След»: все точки с временем, координатами и высотой в метрах (если все не
  помещаются - показан отрезок вокруг выбранной точки); клик по строке выбирает точку и центрирует на ней карту;
- у выбранной точки внизу слева на карте открывается **карточка** со всем, что передавалось в сообщении с этой
  позицией: время приёма, метка, рейс и тип отчёта, маршрут, топливо, температура, ветер, ETA, высота (м и ft),
  турбулентность, время события и неопознанные поля как есть. Повторный клик по выбранному самолёту открывает
  карточку его последней точки;
- **Стрелки ↑ / ↓** листают точки по порядку: назад к более ранним и вперёд, карта следует за точкой. Стрелки сами карту не двигают (её двигают мышью).
В следе хранится до 48 последних позиций борта; повтор той же позиции новой точкой не считается.

## Пути с кириллицей и пробелами

Файлы можно открывать из любых папок, в том числе с русскими названиями
(`F:\acars\Программа\scanerdecoder\acars_logs\acars_log.jsonl`) — это касается
"Импорт JSONL...", "Открыть WAV-файл..." и отчёта по WAV-файлу
(`acars_logs\<имя>.decoded.csv`, имя может быть русским). Раньше такой путь не
открывался и выдавал "Не удалось открыть файл": окно передаёт путь в UTF-8, а обычный
`fopen()` на Windows читает его как ANSI-строку, и кириллица превращалась в мусор.
Теперь путь открывается через Юникод (`_wfopen`, функция `fopen_utf8` в `fileio.c`).
Пути в старой ANSI-кодировке (например, аргумент командной строки) по-прежнему
открываются как раньше. Если файл всё же не открылся, сообщение покажет полный путь и
код ошибки (2 — файла нет, 13 — нет доступа или файл занят другой программой).

## Автозагрузка журнала при запуске

Журнал подгружается **сам при каждом запуске**, без кнопки: сразу работают
отчёты и карта с бортами. Читаются по порядку два файла (если они есть):

1. `acars_logs\acars_log.jsonl` — собственный журнал программы: в него
   дописывается каждое принятое сообщение, и он сохраняется между запусками;
2. `acars_log.jsonl` в рабочей папке — например, ваша копия журнала.

Если журнала нет, ничего не происходит и ничего не показывается; если есть — в
окне вывода появляется строка вида "Загружен журнал, сообщений: 478
(acars_logs\acars_log.jsonl: 478; acars_log.jsonl: 0)". Отключается строкой
`AutoLoad=0` в разделе `[Import]` файла `acars_settings.ini`.

- **Повторы не добавляются.** Одно и то же сообщение (то же время, борт, метка и
  текст) в памяти оказывается один раз — и при автозагрузке двух файлов с общими
  строками, и при повторном нажатии "Импорт JSONL...", и если сообщение уже
  принято вживую. В вашем журнале нашлось 11 строк-дубликатов — они пропускаются
  (поэтому загружается 478 сообщений, а не 489).
- **Читается конец файла.** Если журнал больше 8 МБ, читаются только последние
  8 МБ: в памяти всё равно хранятся последние ~5000 сообщений, а запуск не
  должен задерживаться, сколько бы журнал ни вырос за месяцы приёма. Когда в
  памяти больше 5000, самые старые вытесняются пачкой (десятая часть сразу):
  раньше они вытеснялись по одному, и загрузка большого журнала превращалась в
  десятки секунд зависания (каждое вытеснение сдвигало весь массив, около 12 МБ).
- **Пробелы и мусор.** Разбор допускает пробелы вокруг двоеточия
  (`"addr": "RA73764"`) — так пишут другие инструменты; пустые строки и строки из
  одних пробелов игнорируются молча.

## Импорт журнала (кнопка "Импорт JSONL...")

Если исходной звукозаписи больше нет (стёрлась, не на этом
компьютере и т.п.), а посмотреть маршруты/телеметрию/погоду/
неисправности/карту из уже готового `acars_log.jsonl` хочется — эта
кнопка загружает журнал ОБРАТНО в программу, без повторного
декодирования звука. Все кнопки-отчёты работают с внутренним списком
принятых сообщений, а не напрямую со звуком, так что заполнить этот
список из журнала — то же самое, что заново "принять" эти сообщения.

Разбирается свой собственный формат JSONL (тот же, что пишет сама
программа) — не универсальный JSON-парсер, а узко заточенный под
конкретно наши поля (`timestamp`, `source`, `mode`, `addr`, `label`,
`label_description`, `text`), с полной поддержкой экранирования,
которое сама же программа и производит (переводы строк, кавычки,
управляющие символы вида `\u00XX`). Строки, не похожие на наш формат
(нет поля `timestamp`), просто пропускаются — импорт не прерывается
из-за одной плохой строки; повторы (то же время, борт, метка, текст), уже
бывшие в памяти, тоже пропускаются. Служебные сообщения наземных станций (метка
`SQ`, в заголовке нет адреса борта) импортируются, как и при живом
приёме, с адресом `(?)`. Открой `acars_logs/acars_log.jsonl` (или любой `.jsonl`-отчёт
по отдельному файлу) через эту кнопку.

## Использование

```
acarsdecoder                            (Windows) открыть графический интерфейс - то же самое при запуске двойным кликом
acarsdecoder --gui                      (Windows) то же самое явной командой
acarsdecoder -f запись.wav              декодировать из WAV-файла (авто: IF или готовый звук)
acarsdecoder -f a.wav -f b.wav          можно указать несколько файлов
acarsdecoder --if -f запись.wav         принудительно считать файл "сырым IF"
acarsdecoder --audio -f запись.wav      принудительно считать файл уже готовым ACARS-звуком
acarsdecoder -v -f запись.wav           подробный вывод (резервный конвейер: всплески, фазы, отброшенные кадры)
acarsdecoder --list-devices             (Windows, в т.ч. XP) список устройств записи
acarsdecoder -l                         (Windows, в т.ч. XP) живой приём с устройства по умолчанию
acarsdecoder -l 2                       (Windows, в т.ч. XP) живой приём с устройства №2
```

## Подключение AR5000

### Звук (обязательно)

1. Аудиовыход AR5000 (по возможности — "discriminator/detector out" на
   задней панели, если он выведен; это сигнал до AGC и даёт более чистый
   демодулируемый сигнал, чем обычный AF OUT) → Line In или Mic In
   звуковой карты ПК. Подойдёт любой переходник 3.5мм/RCA под ваш кабель.
2. В настройках записи Windows отключите автоматическое усиление/шумоподавление
   микрофона для этого входа (Панель управления → Звук → Запись →
   Свойства устройства → Уровни/Дополнительно), иначе AGC Windows будет
   мешать демодуляции.
3. Настройте AR5000 на частоту ACARS (в Европе часто 131.550, 131.725,
   131.825, 136.900 МГц; в США — 130.025, 131.550, 131.725, 136.750,
   136.975 и др.) в режиме AM с достаточной полосой (6-8 кГц). Либо
   сделайте это автоматически по RS-232 — см. ниже.
4. Запустите программу (двойным кликом — откроется графический
   интерфейс, см. выше) и нажмите "Начать приём" — как только AR5000
   поймает пакет, в окне появится расшифрованное сообщение.

**Если при открытии устройства записи выходит ошибка** — программа
пробует моно и стерео на 8 частотах дискретизации (8000-96000 Гц), а
если выбранное устройство не открылось совсем - ещё и устройство по
умолчанию через системный "маппер". Если не подошло ничего, в лог
выводится, **что именно ответил драйвер** (реальные коды ошибок и
сколько раз каждый встретился), а также что само устройство сообщает о
себе (имя, число каналов, маска поддерживаемых форматов).

Открытие устройства теперь идёт через `CALLBACK_NULL` (простой опрос
готовности буферов, без события Windows в качестве параметра
`waveInOpen`) - раньше использовался `CALLBACK_EVENT`, и на одной
системе (Realtek, Windows) все 16 комбинаций формат/каналы отказывали
с кодом MMSYSERR_INVALPARAM (11 - "неверный параметр передан системной
функции"), а не WAVERR_BADFORMAT ("формат не поддерживается") - то
есть настоящей причиной был не формат звука, а именно объект
события в вызове. `CALLBACK_NULL` исключает этот параметр из вызова
целиком - самый примитивный и совместимый режим работы с waveIn.
Также исправлено отображение имени устройства в диагностическом
сообщении - раньше оно печаталось в системной ANSI-кодировке напрямую,
и кириллица/другие не-ASCII символы превращались в "квадратики";
теперь корректно перекодируется в UTF-8 перед выводом.

Если ошибка сохраняется и после этого, в сообщении также есть
чек-лист, что проверить (раньше причиной бывает занятое другой
программой устройство, запрет доступа к микрофону в Параметрах
Windows -> Конфиденциальность, или отключённое устройство).

### Управление по RS-232 (опционально, `src/ar5000.c`)

Кроме звука можно подключить AR5000 к отдельному COM-порту (обычному
последовательному, включая USB↔RS232 переходники) — тогда программа
сама настроит режим/полосу и сможет переключать частоту, без
необходимости лезть на переднюю панель приёмника.

1. Соедините разъём **REMOTE** на задней панели AR5000 с COM-портом
   компьютера (9-контактный RS232, прямой кабель — не нуль-модемный).
2. В CONFIG-меню самого приёмника посмотрите/задайте скорость обмена
   (4800, 9600 или 19200 бод) — она должна СОВПАДАТЬ с тем, что вы
   укажете в программе.
3. В GUI: укажите COM-порт (например, `COM3`) и скорость, нажмите
   "Подключить". Программа сама пошлёт запрос версии (для проверки
   связи) и переключит приёмник в режим/полосу, которые в этот момент
   выбраны в выпадающих списках **"Режим"** (FM/AM/LSB/USB/CW/Sync AM/
   SAL/SAH — по умолчанию AM, то, что нужно для ACARS) и **"Полоса"**
   (0.5-220 кГц, по умолчанию 6 кГц). Их можно менять и ПОСЛЕ
   подключения в любой момент — выбор сразу отправляется приёмнику
   (команды `MD`/`BW`), без необходимости переподключаться. Дальше
   впишите частоту в МГц и нажмите "Настроить", либо выберите готовую
   частоту из выпадающего списка (автоматически применяется сразу).
   Статус-строка ниже показывает уровень сигнала (обновляется раз в
   секунду) — удобно, чтобы увидеть, что канал реально "живой".
4. Из консоли то же самое: `acarsdecoder.exe --ar5000-port COM3
   --ar5000-freq 131.725 -l` — подключится, настроит режим/полосу/
   частоту, запустит живой приём, и корректно отключится (командой
   `EX`, освобождающей переднюю панель) по Ctrl+C.
5. Кнопка **"↻ Сканировать"** (в GUI, требует подключения к приёмнику)
   — автоматически перебирает частые частоты ACARS (Европа + США, тот
   же список, что и в выпадающем меню пресетов): на каждой слушает
   3 секунды; если шумоподавитель открылся (кто-то передаёт) —
   задерживается на ней ещё 15 секунд, давая декодеру шанс поймать
   пакет, и только потом едет дальше; если тихо — сразу к следующей.
   Само декодирование сканер не трогает — он только переключает
   частоту по RS-232, а живой приём со звуковой карты (тот же
   работающий конвейер) разбирает всё, что придёт, независимо от того,
   что происходит на COM-порту. Поэтому для сканирования, помимо
   подключения к приёмнику по RS-232, нужен ещё и отдельно запущенный
   живой приём ("▶ Начать приём") — без него сканер просто переключает
   частоты вхолостую, ничего не декодируя.
6. Кнопка **"Список памяти"** (рядом — выбор банка 0-9) — читает
   содержимое выбранного банка памяти приёмника (команда `MA`, до 100
   каналов) и показывает только ЗАНЯТЫЕ каналы (частота, режим,
   текстовый комментарий, если задан на самом приёмнике). Формат
   ответа AR5000 на эту команду многострочный (до 100 строк на банк,
   присылается блоками по 10) — читается и разбирается отдельно от
   остальных, однострочных команд. Пустые каналы не показываются,
   чтобы список оставался читаемым. Разбор строк проверен на реальных
   примерах ответа из документации AOR, включая пустые/непустые
   каналы и разное количество полей.

Протокол — стандартный, задокументированный производителем
("AR5000 RS-232C Command List"): ASCII-команды вида `RFnnnnnnnnnn`
(частота в Гц), `MDn` (режим), `BWn` (полоса), `LM` (уровень сигнала)
и т.д., завершаются символом `<CR>`. Параметры порта: 8 бит данных, 2
стоп-бита, без чётности, программное управление потоком XON/XOFF (не
аппаратное RTS/CTS). Источники, по которым сверялись конкретные команды
и формат ответов, перечислены в `include/ar5000.h`.

С появлением сканера обмен с приёмником теперь может идти сразу из
**двух** потоков одновременно (фоновый опрос уровня сигнала раз в
секунду + сам сканер) — добавлена блокировка (`CRITICAL_SECTION` в
`ar5000.c`, `ar5000_module_init()`) вокруг каждого цикла "команда →
ответ", чтобы их обмены гарантированно не перемешивались на проводе.

При отладке (уже после первых тестов GUI) обнаружился реальный баг:
частота (в МГц, например "131.725") форматировалась через
`wsprintfW(..., L"%.3f", ...)` — а `wsprintfW` (упрощённая функция из
`user32`, а не полноценный printf из CRT) **вообще не поддерживает
спецификатор `%f`** — это давняя, задокументированная особенность этой
функции. Список пресетов частот, поле частоты при выборе пресета и
статус во время сканирования выводили бы не число, а мусор. Исправлено
через ручное форматирование (`format_mhz()` в `gui_win.c`) с проверенным
на граничных случаях (перенос при округлении) кодом.

**Не тестировалось на реальном приёмнике** — реализовано строго по
документированному протоколу и внимательно вычитано вручную (как и
остальной Windows-специфичный код в этой сессии — собрать и проверить
на настоящем железе можно только на вашей машине), но при первом
подключении возможны нюансы конкретно вашего экземпляра прошивки —
дайте знать, если что-то не сойдётся.

## Коррекция ошибок (FEC, `framesync.c`)

Если у собранного кадра не сошёлся CRC, декодер пытается его исправить —
но не слепым перебором всех бит подряд (как было раньше), а по
чётности символов: ACARS передаёт каждый символ с нечётной чётностью
(7 бит данных + 1 бит чётности, сумма единичных бит должна быть
нечётной — см. `add_parity()` в `selftest.c`). Байт с чётным числом
единиц — явный признак битового сбоя именно в нём, это резко сужает
перебор и, что важнее, риск случайного ложного "исправления" (у CRC-16
всего 65536 возможных значений — при слепом переборе всех пар бит по
кадру длиной хотя бы в пару сотен байт случайное совпадение становится
почти неизбежным, а при переборе 8 или 64 вариантов, подсказанных
чётностью конкретных байт, — пренебрежимо маловероятно):

- **0 "подозрительных" байт** — подстраховка: прежний слепой перебор
  одного бита по всему кадру.
- **1 байт** — перебираем 8 бит именно в нём.
- **2 байта** — перебираем 8×8 = 64 комбинации (по одному биту в
  каждом) — это и есть полноценная коррекция ДВУХ битовых ошибок,
  чего раньше decoder не умел вовсе.
- **3+ байта** — кадр слишком испорчен, чтобы доверять исправлению; не
  трогаем.

Два последних байта кадра (сами байты CRC/BCS) в проверку чётности не
включаются — это не символы, а сырое двоичное значение, к ним
конвенция нечётной чётности не применяется.

Проверено отдельным тестом (не просто "должно работать"): кадр без
ошибок, с 1 битовой ошибкой, с 2 ошибками в разных байтах (успешно
исправляются все три случая) и намеренно граничные случаи — 3 ошибки,
и 2 ошибки в ОДНОМ байте (чётность их не видит, комбинация отменяет
друг друга) — оба варианта корректно остаются непроверенными, а не
"исправляются" наугад.

## Маршрут рейса (`ooi_parse.c`)

Часть OOOI-сообщений (автоматические отчёты о фазах полёта — ушёл от
гейта / взлетел / сел / прибыл на гейт) содержат в тексте номер рейса
и аэропорты вылета/назначения в **стандартном, официально
задокументированном** формате "FI" (Flight Identification):

```
FI JA401/AN CC-AWE/DA SPJC/DS SCEL/OT 0030/FB /BF
```

(JA401 — номер рейса, CC-AWE — регистрация борта, SPJC — аэропорт
вылета (код ICAO), SCEL — аэропорт назначения, 0030 — время ухода от
гейта, UTC). Источник — "ACARS: Data Elements and Message Examples",
опубликовано OAG (авиационная информационная компания):
<https://www.oag.com/hubfs/Inbound-Services/OAG-ACARS-OOOI-Message-Types-and-Examples.pdf>.

Декодер распознаёт этот формат и показывает разобранные поля (рейс,
вылет, назначение, времена) отдельным блоком под текстом сообщения — в
консоли, в GUI-логе и в `acars_logs/acars_log.csv`/`.jsonl` (колонки
`ooi_flight_id`, `ooi_departure`, `ooi_destination`, `ooi_arrival`).

**Честная оговорка** — почему это НЕ универсальное решение "куда летит
любой борт": как прямо пишет тот же источник, у ACARS "около сотни
стандартных форматов и практически неограниченное количество
фирменных форматов конкретных авиакомпаний" для одной и той же
информации. У многих крупных перевозчиков (Air Canada, British Airways
и др.) — полностью другой текстовый формат для маршрута, который этот
разбор не распознает и не пытается угадать (специально, чтобы не
выдать частичное/случайное совпадение за настоящий маршрут). Так что
маршрут покажется не для каждого сообщения даже среди тех, что в
принципе его несут — только там, где авиакомпания использует именно
этот, "стандартный" OAG-формат.

Полноценное определение маршрута для **любого** борта в реальном
времени (независимо от формата конкретной авиакомпании) потребовало бы
подключения внешнего сервиса живых данных о рейсах (например,
FlightAware, ADS-B Exchange, OpenSky live states API) — это уже не
статический файл-справочник вроде `aircraft_db.csv`, а постоянное
интернет-соединение с сторонним сервисом, что меняет саму природу
программы (сейчас она полностью автономна, работает без интернета) и
поднимает вопросы лимитов запросов/условий использования конкретного
API. Если это действительно нужно — отдельная, более крупная задача.

## Разбор ADS-C/CPDLC (`arinc622.c`)

Часть меток ACARS (например `AT`, специфичные для конкретной
авиакомпании) несут не текст, а служебные данные диспетчерского
слежения (ADS-C) и цифровой связи с диспетчером (CPDLC) — это
отдельные, официально стандартизированные протоколы (ARINC 622/745,
ICAO Doc 4444), упакованные поверх обычного текстового поля ACARS.

**Что реализовано.** Тело таких сообщений начинается с "/" и имеет вид
конверта ARINC 622:
```
/<наземная станция>.<IMI>.<борт><hex-данные><CRC, 4 hex-цифры>
```
Например (реальный пример из вывода `acarsdec`): `/SOUCAYA.AT1.F-GSPK618AD60600F470`.
Декодер надёжно разбирает этот конверт — кто отправитель (наземная
станция), что за тип сообщения (IMI — расшифровка по известному
списку кодов: `AT1`=CPDLC-сообщение, `CR1`/`CC1`/`DR1`=установка/
подтверждение/разрыв CPDLC-соединения, `ADS`/`DIS`=ADS-C-сообщение/
разрыв), какой борт. Граница "борт / данные" определяется НАДЁЖНО (не
угадыванием) — сверяется с уже известным номером борта из заголовка
самого ACARS-сообщения. Результат виден в консоли/GUI-логе (отдельным
блоком под текстом сообщения) и в `acars_logs/acars_log.csv`/`.jsonl`
(колонки `arinc622_imi`, `arinc622_imi_desc`, `arinc622_ground_station`).

**Что НЕ реализовано, и почему.** Сами hex-данные внутри конверта —
это ASN.1 PER-кодированное содержимое (собственно координаты, высота,
текст команды диспетчера и т.п.) по схемам FANS-1/A CPDLC и ADS-C.
Полноценный разбор ЭТОГО уровня — задача сопоставимого объёма с
написанием небольшого ASN.1-компилятора под конкретные схемы; именно
поэтому даже сам `acarsdec` не реализует это самостоятельно, а
использует отдельную специализированную библиотеку —
[libacars](https://github.com/szpajder/libacars). Выдумывать разбор
этих байт без сверки с проверенной эталонной реализацией не стали:
неверно "расшифрованные" координаты или диспетчерская команда в
авиационном инструменте хуже, чем честно показанные необработанные
данные. Хотите координаты/высоту из ADS-C или текст команд из CPDLC —
следующий, отдельный шаг развития — подключить `libacars` (готовая,
проверенная библиотека на C) и передавать ей `hex_payload` из
`Arinc622Envelope` для дальнейшего разбора.

Проверено тестом на реальном примере сообщения (см. выше) — конверт
разбирается корректно; для текста, который лишь СЛУЧАЙНО похож по
структуре (начинается с "/", есть точки), но борт не совпадает с
заголовком сообщения — корректно НЕ распознаётся как конверт (не
гадаем).

## База данных бортов (`aircraft_db.c`)

Регистрационный номер борта (поле `Addr`, например `.VP-BSY`) можно
дополнительно обогатить типом самолёта и авиакомпанией-оператором. Как
и с таблицей меток, мы не выдумываем эти данные и не поставляем их
вместе с программой (это десятки-сотни тысяч записей, вопрос
актуальности и лицензии чужих данных) — вместо этого декодер читает
файл `aircraft_db.csv`, если он лежит рядом с программой, в **реальном
публичном формате базы данных воздушных судов OpenSky Network**
(лицензия CC-BY-SA, официальный сайт
<https://opensky-network.org/aircraft-database>): скачали файл оттуда,
положили рядом с `.exe` под именем `aircraft_db.csv` — и обогащение
заработало само, без всякой конвертации формата.

Нужные колонки (`registration`, `icao24`, `manufacturername`/`manufacturericao`,
`model`, `typecode`, `operator`) определяются по строке заголовка
файла, а не по жёстко заданным номерам позиций — устойчивее к мелким
изменениям формата. Файла нет — ничего не ломается, обогащение просто
не работает (полностью необязательная функция). При успешной загрузке
при старте программы выводится строка вида "База бортов: загружено
N записей". Результат виден в консоли/GUI-логе (строкой под `Addr`) и
в `acars_logs/acars_log.csv`/`.jsonl` (колонки `aircraft_manufacturer`,
`aircraft_model`, `aircraft_typecode`, `aircraft_operator`).

**Поиск не зависит от дефиса, регистра и ведущей точки.** Раньше `RA73104`
из ACARS не находил запись `RA-73104` из базы OpenSky: в 7-символьное поле
адреса ACARS дефис не влезает у 8-значных регистраций, и для российских
бортов тип и оператор не подставлялись. Теперь сравнение идёт по ключу из одних
букв и цифр в верхнем регистре (`RA73104`, `.ra-73104`, `RA-73104` — одно и то
же). Колонка `icao24` (код Mode S) читается и используется окном карты для
точного запроса фото.

Проверено тестом на данных в реальном формате OpenSky (с настоящими
именами колонок и структурой строк) — поиск по регистрации, разбор
пустых полей и явно отсутствующая в базе регистрация (корректно не
находится, а не выдаёт что попало) — всё работает как задумано.

## База данных аэропортов (`airport_db.c`)

Коды аэропортов ICAO (4 буквы, например `UUEE` — Москва-Шереметьево,
`EVRA` — Рига), которые встречаются в маршрутах, можно расшифровать в
название и город. Тот же принцип, что и с базой бортов: файл не
поставляется вместе с программой — читаем `airport_db.csv`, если он
лежит рядом с программой, в **реальном публичном формате базы данных
аэропортов OurAirports** (общественное достояние, официальный сайт
<https://ourairports.com/data/>, сам файл целиком —
<https://ourairports.com/data/airports.csv>, ~80000 аэропортов и
площадок по всему миру): скачали, положили рядом с `.exe` под именем
`airport_db.csv` — обогащение заработало само.

Нужные колонки (`ident`, `name`, `municipality`, `iso_country`)
определяются по строке заголовка файла. Используется два способа
показать маршрут:

1. **Через уже разобранный формат OOOI FI** (см. раздел выше) — там
   роли полей (вылет/назначение) уже надёжно известны, коды аэропортов
   просто дополняются названием и городом.
2. **Резервный поиск пары кодов подряд без разделителя** — в некоторых
   форматах телеметрии (например, у сообщений с меткой H1 вида
   `...VP-BWGEVRAUUEE0MAR...`) два кода ICAO идут прямо друг за другом
   без всякого разделителя. Если формат FI не сработал, декодер ищет
   такую пару в тексте — но **не** утверждает, какой из двух код вылет,
   а какой назначение (это уже вопрос конкретного, незадокументированного
   формата), и явно помечает находку как "порядок не подтверждён".
   Правило нарочно строгое (нужна ПАРА подряд идущих известных кодов, а
   не любой один) — это резко снижает риск случайного совпадения на
   посторонних данных телеметрии по сравнению с поиском одиночных
   4-буквенных последовательностей в базе из ~80000 записей.

Кнопка **"Маршруты"** в GUI (рядом со "Статистика") показывает сводку
по всем бортам, для которых за сессию удалось найти маршрут тем или
другим способом — с пометкой, откуда взяты роли полей.

Проверено тестом на точном тексте реального принятого сообщения
(тот самый пример `EVRAUUEE`) — пара корректно находится и
расшифровывается в "Рига → Москва (Шереметьево)".

## Отчёты о неисправностях (`cfdiu_fault.c`)

Часть сообщений с меткой `H1` — это отчёты CFDIU (Central Fault
Display Interface Unit, централизованный регистратор неисправностей),
начинающиеся с `#CFB`. Внутри — человекочитаемое описание на
английском, например:

```
#CFBWRN/WN26092911220034580006NAV GPS2 FAULT
#CFBFLR/FR26092910490034360006GPS ANTENNA2(43RT2)/COAX CABLE/MMR2(40RT2)
```

Декодер отдельно выделяет: тип записи (`FLR` — отказ, `WRN` —
предупреждение) и само описание неисправности. **Честная оговорка**:
между типом записи и описанием идёт блок из ~20 цифр, по всем
признакам дата/время + внутренний код — но точная разбивка этих цифр
на подполя нигде не подтверждена (официальная документация CFDIU
платная), поэтому блок сохраняется и показывается целиком, без
попытки угадать его внутреннюю структуру.

Формат найден и проверен по нескольким реальным принятым сообщениям
(не по документации) — 6 тестов, включая проверку, что обычный текст
и соседний формат `#DFB` (DFDAU, другая бортовая система) корректно
НЕ распознаются как CFDIU-отчёт.

Кнопка **"Неисправности"** в GUI показывает сводку найденных за сессию
отчётов по бортам, без повторов одинаковых описаний.

## Телеметрия ASU/AFL (`asu_telemetry.c`)

Метки `26`/`27` (см. labels.h) у бортов формата ASU/AFL (Россия/
Аэрофлот) несут не просто текст, а подписанные поля — топливо,
температура, ветер, координаты, расчётное время прибытия, высота:

```
FUEL   69
TEMP- 52
WDIR19867
WSPD  16
LATN 55.835
LONE 43.376
ETA1101
ALT  35992
```

Поля разбираются построчно по самим подписям (`FUEL`, `TEMP`, `WDIR`,
`WSPD`, `LATN`/`LATS`, `LONE`/`LONW`, `ETA`, `ALT`) — это стандартные
авиационные сокращения, не требующие расшифровки извне. Первая строка
сообщения (номер, тип отчёта, коды аэропортов) этим модулем не
трогается — границы её отдельных полей нигде не подтверждены; коды
аэропортов из неё показывает отдельно `airport_db.c` (см. выше).

Результат попадает в консольный/GUI-вывод и в CSV/JSON (колонки
`asu_fuel`, `asu_temp`, `asu_wind_dir`, `asu_wind_speed`, `asu_lat`,
`asu_lon`, `asu_eta`, `asu_alt`), так же как `cfdiu_severity`/
`cfdiu_description` для отчётов о неисправностях.

Кнопка **"Телеметрия"** в GUI показывает по каждому борту ПОСЛЕДНЕЕ
известное за сессию значение каждого поля (не список всех замеров
подряд) — удобно, чтобы быстро посмотреть текущий остаток топлива,
координаты и высоту конкретного борта, не листая весь лог.

## Расшифровка текстов по структуре ARINC 620 (`acars_report.c`)

Модуль появился по результатам разбора журнала в 2145 сообщений (104 борта; почти
все русские рейсы Аэрофлота, Россия, Уральских авиалиний, S7, Nordwind плюс иностранные).
Он показывается в окне **«Подробности»** (блок «Расшифровка») и в консольном выводе.

**Заголовок даунлинка.** Почти любой текст с борта начинается с `M56A` + `SU1603`:
порядковый номер сообщения (MSN, 4 символа) и идентификатор рейса (код IATA + номер).
Рейс показывается вместе с названием авиакомпании (короткий список надёжно известных
кодов: SU, FV, U6, S7, N4, DP, UT, DV, GF, MU, J2, PK, HY, RJ, AA, A9 и т.д.).
Нули вместо номера рейса (`FV0000`) означают, что рейс ещё не введён.

**Отчёты группы Аэрофлот/Россия** (метки 26, 27, 12, 14, 15, 39), первая строка
`POS01AFL1603   /29151006UWWWUUEE`: тип события, позывной, число и время UTC,
аэропорт вылета и назначения (с названием, если загружена база аэропортов).
Время подтверждено: журнал хранит местное время (МСК = UTC+3), а группа `1006`
соответствует 13:06 МСК. Типы: POS, ETA, OFF, INN, SFI подтверждены по содержимому
(SFI содержит времена OUT/OFF/ON/IN и интервалы, которые сходятся арифметически);
PBS/ADC/LDC/LDO/APS/RTG помечены как «вероятно» - по порядку событий и аббревиатурам,
документации нет.

**Строки данных.** FOB/FUEL - остаток топлива (вероятно, сотни кг: у A321 после взлёта
`FOB 187`, т.е. ~18.7 т), TEMP - °C, WDIR - направление ветра (все 65 значений в
журнале лежат в 0-35999, поэтому читается как сотые доли градуса: `19867` = 198.67°;
формат НЕ подтверждён документацией), WSPD - вероятно, узлы, LATN/LONE - координаты,
ETA - расчётное прибытие UTC, ALT - вероятно, футы, TUR - турбулентность (в данных поле
всегда пустое). Время события (`072128`) может быть заметно раньше времени приёма -
борт отправляет сообщение позже самого события.

**Метка 16** (Аэрофлот/Nordwind и др.): поля через запятую - время, высота (футы), ETA,
число неизвестного смысла, координаты (`MMMM.MMM` = навигационных данных нет).
**Метка SA**: `0`+код (`EV`/`LH`)+время ЧЧММСС+`V` - время подтверждено, смысл кода нет.
**Метка 5U**: запрос погоды `UMMS-SA` (SA = METAR, FT = TAF).
**Метка SQ**: исправлено описание - это служебный сигнал наземной станции (squitter),
а не «свободный текст».
**Уплинки**: ATIS (A9: тип ARR/DEP/ENR, аэродром, литера), отказ диспетчерской службы
(A4, `FSM`: дата в формате ггммдд), принтерные Type B сообщения (C1: отправитель,
время, борт `AN`, номер подтверждения `MA`), запрос ATIS (B9).

Что НЕ расшифровывается и честно так и написано: поля `EONT/EOFT/FBOU/AGFF...` в
сводках SFI/APS, смысл кодов `TI2`/`FS2`, число в метке 16, пара цифр между числом и
временем в первой строке.

**Тесты:** `tests/test_report.c` (строки из реального журнала + обрезанные/мусорные
тексты, под AddressSanitizer):

    gcc -g -Wall -fsanitize=address,undefined -Iinclude -o test_report tests/test_report.c src/acars_report.c src/airport_db.c && ./test_report

## Погода METAR (`metar.c`)

Часть сообщений (чаще всего с меткой `RA`) несут экипажу настоящие
сводки погоды METAR (Meteorological Aerodrome Report) — ежечасные/
получасовые отчёты о фактической погоде аэродрома. В отличие от
большинства фирменных форматов в этом проекте, METAR — **настоящий
международный стандарт** (ICAO Annex 3 / WMO № 782), поэтому разбирается
полностью, без оговорок про "неподтверждённый формат":

```
LTBA 160750Z 19006KT 9999 SCT035 13/08 Q1018 NOSIG=
```

раскладывается на: аэродром (код ICAO, при наличии `airport_db.csv`
дополняется названием/городом), время сводки (UTC), ветер (направление,
скорость, порывы, переменное направление), видимость или признак CAVOK
("всё отлично"), явления погоды (дождь/снег/туман/дымка и т.п. —
переведены на русский по стандартной таблице ICAO), облачность
(тип и высота — высота в METAR задаётся в сотнях футов, учтено),
температура и точка росы, давление (QNH), прогноз тренда (NOSIG/TEMPO/
BECMG).

В одном ACARS-сообщении может быть несколько сводок подряд (для разных
аэродромов по маршруту), разделённых знаком `=` — разбираются все.
Если заголовок первой сводки обрезан (бывает при неполном приёме) —
она корректно пропускается, а не разбирается с выдуманными данными.

Результат — в консольном/GUI-выводе и в CSV/JSON (колонки
`metar_count`, `metar_stations` — количество и список аэродромов в
сообщении; полный человекочитаемый текст сводки смотрите в выводе).
Кнопка **"Погода"** в GUI показывает все найденные за сессию сводки,
без повторов одной и той же (по коду станции и времени).

## Значок приложения

`resources/acars.ico` (сгенерирован программно, радарная тема: тёмный
круг, кольца, зелёный сектор развёртки, силуэт самолёта) встраивается
в `.exe` как настоящий Windows-ресурс через `resources/acars.rc` +
`windres` — виден в Проводнике, на панели задач, в Alt-Tab, а не только
внутри самого окна программы. При сборке через CMake обрабатывается
автоматически (CMake сам вызывает нужный компилятор ресурсов). Если
почему-то не подгрузится (например, кто-то соберёт `.exe` без
компиляции `.rc`) — код откатывается на системный значок по умолчанию,
чтобы окно в любом случае открылось.

## Известные ограничения / куда развивать дальше

- **Полярность/180°-неоднозначность** (`~SYN` = `0xE9`) в `framesync.c`
  обрабатывается как простой флаг инверсии битов на уровне парсера
  кадра — в оригинале это двусторонняя обратная связь с самим
  демодулятором (`MskS ^= 2`), у нас упрощено (не обратной связью в
  `mskpll.c`, а инверсией во `framesync.c`); на практике на всех
  тестах отработало корректно, но это не побитово точная копия.
- **Таблица меток** (`include/labels.h`) существенно расширена и
  сверена по двум независимым источникам (систематическая таблица
  ARINC 620 и подборка реальных примеров по авиакомпаниям — ссылки в
  самом файле), но всё равно не претендует на полноту: у одной только
  IATA около сотни стандартных форматов, и у каждой авиакомпании
  вдобавок свои собственные. Некоторые метки помечены как
  "предположительно"/"варьируется по авиакомпании" — их значение либо
  не подтверждено вторым источником, либо реально отличается от
  перевозчика к перевозчику. Расширяется тривиально — дописываете
  строки в массив.
- Разбор полей (mode/addr/ack/label/blockid/text) сделан по общей схеме
  ARINC 618 и покрывает подавляющее большинство сообщений. Конверт
  ARINC-622 приложений (ADS-C/CPDLC) разбирается (см. раздел выше) —
  но сами ASN.1-данные внутри него остаются нерасшифрованными
  (нужен отдельный ASN.1-декодер, например `libacars`). В тексте могут
  быть непечатаемые байты — это нормально, framesync их не отбрасывает.

## Маршрут «откуда → куда» и все сообщения борта

* **Маршрут** берётся из служебных отчётов Аэрофлота/России (первая строка отчёта содержит аэропорты вылета и назначения; это
  проверено: события «на земле» в журнале попадают в нужный аэропорт с точностью 1–2 км). У других авиакомпаний маршрут в сообщениях
  не передаётся — тогда на карте написано «Маршрут в сообщениях борта не передан». Пара вылет/назначение всегда берётся из ОДНОГО
  сообщения, последнего по времени.
* **Панель карты** показывает рейс, «Откуда», «Куда» (код ICAO, город, название) и расстояние по прямой до аэропорта назначения.
  **На карте** для выбранного борта рисуются ромбы аэропортов, тонкая линия вылет → назначение и пунктир от самолёта до пункта назначения.
* Названия и положение аэропортов берутся из `airport_db.csv` (OurAirports, колонки `latitude_deg`/`longitude_deg`); для ~35 самых
  частых аэропортов есть встроенная таблица, так что маршрут виден и без файла.
* **Все сообщения борта**: в панели карты — строка «▶ Все сообщения борта...» (или клавиша `B`). Спрашивает период (пусто — все дни
  журнала; можно часы одного дня или несколько дней) и открывает отчёт: сводка, рейсы с маршрутами, последняя позиция и расстояния до
  аэропортов, затем хронология сообщений с расшифровкой (пустые служебные подтверждения скрыты, их число указано).
  Читается полный журнал `acars_logs\acars_log.jsonl`, поэтому доступны все накопленные дни.
* В окне «Выгрузка…» появилось поле **«Только борт»** — Excel/JSONL по одному борту за любой период.
* Тесты: `tests/test_coords.c` (проекции туда-обратно на всех масштабах, знаки S/W, маршрут), `tests/test_route.c` (журнал → отчёт по борту
  и сверка с аэропортами), `tests/test_export.c`.

## Порядок точек следа

Борт иногда досылает накопленные сообщения, и они доходят не по порядку (пример: RA73115 — приняты M25A, M20A, M22A; по порядку приёма
след рисовал «треугольник»). Теперь точки следа упорядочиваются по номеру сообщения борта (MSN: M20A → M22A → M25A), если сообщения
приняты в пределах 5 минут друг от друга; повторный приём того же сообщения не добавляет точку. Последняя позиция борта — конец
упорядоченного следа. В таблицах и отчётах по борту сообщения остаются в порядке приёма (время приёма видно в каждой строке).

## Ветер

Поля `WDIR`/`WSPD` из отчётов показываются так: «из 333.6° (ССЗ), 75 уз (139 км/ч, 39 м/с)».
* **Направление** — откуда дует ветер (как в авиации), в градусах от севера по часовой стрелке; в скобках сторона света. Число в сообщении
  читается как сотые доли градуса (33359 → 333.59°).
* **Скорость** — узлы, с пересчётом в км/ч и м/с.
Оба предположения документацией не подтверждены, но косвенно сходятся: направления в журнале 290–360° (типичный западный перенос), а скорость растёт с высотой
(5 уз у земли, 11 уз на 6800 ft, 38 на 23000, 61 на 32600, 75–85 на 35000 ft). Об этом сказано и в расшифровке, и на листе «Пояснения» в Excel.

## Список бортов на карте

Каждый борт в списке — две строки: регистрация и высота (м и ft), ниже мелко — «следов: N» и расчётное время прибытия
«ETA 11:42 UTC (14:42 МСК)». В карточке выбранного борта ETA показано так же. Когда борт выбран, в списке видно 4 борта (остальные —
колёсиком мыши), иначе 10.

След борта начинается заново при смене рейса (номер рейса из заголовка сообщения) или после перерыва больше 4 часов: иначе линия
соединяла посадку одного рейса со взлётом другого (RA73170: прилёт AFL1569 из Тюмени и через несколько часов вылет AFL1954 в Актау).

Отложенные сообщения: борт иногда досылает накопленные отчёты спустя дни (RA89042 на 6-е число передал события 3-го: Москва → Петербург →
Москва). Число месяца событий стоит в заголовке отчёта; если оно отличается от дня приёма на 2 и более дней, такая позиция на карту
не наносится (в отчёте по борту и в таблицах остаётся).

## Что попадает в выгрузку и в отчёт по борту

«Выгрузка…» и «Все сообщения борта» берут данные из трёх источников сразу: журнал программы (`acars_logs\acars_log.jsonl` — в него пишется
и живой приём, и расшифровка WAV), файлы JSONL, загруженные кнопкой «Импорт JSONL...» в этом сеансе, и всё, что сейчас в памяти программы.
Повторы между источниками отбрасываются по содержимому (время, борт, метка, начало текста), так что одно сообщение не задваивается.

## Windows XP

Программа с самого начала собирается под XP (`_WIN32_WINNT=0x0501`, звук через `waveIn`, GDI+ и wininet подгружаются на лету). Что учтено и что надо знать:
* **Чем собирать.** Нужен MinGW-w64 с библиотекой **msvcrt** (не UCRT): сборки на UCRT (например, `ucrt64` в MSYS2) на XP не запускаются.
  Подойдёт `mingw32`/`mingw64` из MSYS2 (msvcrt) или winlibs с пометкой «msvcrt». В `Makefile` добавлены ключи, задающие версию подсистемы 5.1 —
  иначе у новых binutils XP пишет «не является приложением Win32».
* **Шрифт.** На XP нет Segoe UI — используется Tahoma; вместо ▶ рисуется ► (в Tahoma нет ▶).
* **Интернет-подложка.** XP не умеет TLS 1.2, поэтому `https`-тайлы OpenStreetMap и фотографии planespotters на XP не загрузятся.
  Карта работает с **локальным кэшем SAS.Planet** (стили «кэш SAS.Planet»), свои фото берутся из папки `aircraft_photos`. Всё остальное
  (приём, расшифровка, отчёты, Excel, журнал) от интернета не зависит.
* Excel-выгрузка (`.xlsx`) открывается в Excel 2007+ или LibreOffice; в Excel 2003 понадобится пакет совместимости.
* Я не могу запустить XP, поэтому проверено только то, что сборка не использует API новее XP. Если что-то не заработает — пришлите текст ошибки.

## Карта: аэропорты, история, маршрут без линий

* **A** — показать/скрыть аэропорты. Серые ромбы с кодами ICAO — все известные аэропорты (встроенная таблица / `airport_db.csv`) и аэропорты
  вылета/назначения бортов. У выбранного борта вылет и назначение рисуются крупно, у назначения подписано «N км по прямой».
* Пунктир «самолёт → аэропорт назначения» и линия вылет → назначение убраны: они вводили в заблуждение (рейсы идут по трассам и с
  обходами). Пройденный путь показывает след борта.
* **T** — проигрывание истории. Внизу карты появляется полоса времени (от первого до последнего сообщения с координатами). Потяните ползунок
  мышью или нажимайте **← / →** (±10 минут, с Ctrl ±1 час); **Пробел** — запустить/остановить проигрывание (10 минут истории за 0,25 с);
  **T** ещё раз — вернуться к текущему состоянию. На карте и в списке показаны борта, какими они были на выбранный момент (след, позиция,
  маршрут); борт, от которого последнее сообщение было больше 2 часов назад, скрывается. Точность ограничена тем, что борт сообщил о себе:
  между отчётами позиции нет.

## Поиск борта

- **Главная таблица:** поле «Борт» справа от «Поиск» оставляет в таблице только сообщения этого борта
  (`RA73704`, `ra-73704`, `.RA 73704` — одно и то же). Двойной щелчок по строке подставляет борт этой строки.
  При вводе в любое из двух полей таблица включается автоматически, чтобы результат был виден сразу.
- **Карта:** поле поиска в панели (или `/`, `Ctrl+F`) ищет по регистрации, рейсу, ICAO аэропортов вылета/назначения,
  типу, компании, Mode S. Один найденный борт выбирается и карта переезжает к нему; несколько — карта охватывает
  все, найденные обведены жёлтым кольцом, `Enter` выбирает следующий. `Esc` очищает поиск.

## Банки памяти AR5000

Кнопка **«Банки памяти...»** (рядом с выбором банка) открывает отдельное окно:
- «Прочитать» читает выбранный банк или все 10 банков (команда `MA`, по 10 каналов за запрос), окно не зависает, есть «Стоп».
- Таблица: банк, канал, частота, режим, шаг, пропуск при сканировании (`MP`), полоса, аттенюатор, комментарий и
  **сырая строка ответа приёмника**. Сортировка по клику на заголовок, фильтр по тексту, переключатель «Показывать пустые».
- Внизу журнал обмена: `->` команда, `<-` ответ, `!` замечание (неполный блок, чужой банк, нераспознанная строка,
  приёмник молчит). По нему видно, что реально происходит на порту.
- В списке банков видна сводка («Банк 3 - занято 27 из 100»).
- Двойной щелчок по каналу (или «Настроить на канал») посылает `MR`, затем спрашивает у приёмника частоту (`RF`) и
  сообщает, совпала ли она с памятью; частота и режим подставляются в главное окно.
- «Экспорт в CSV...» сохраняет то, что показано в таблице (UTF-8, разделитель `;`).
Перед каждым `MA` очищается буфер приёма, чтобы остатки прежних ответов не сдвигали строки.

## Поиск в окнах отчётов

Поле поиска окон «Подробности», «Статистика», «Маршруты», «Телеметрия», «Погода», «Неисправности», «Все сообщения
борта» и других ищет по ходу набора. Окно само прокручивается так, чтобы найденное слово оказалось примерно посередине;
все вхождения подсвечены тусклым фоном, текущее — ярче; `Enter` — к следующему, `Ctrl+F` из текста — в поле поиска.
